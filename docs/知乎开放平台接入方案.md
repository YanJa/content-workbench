# 知乎数据开放平台接入方案

> 目标：①每天自动抓取知乎热榜并落库 ②用户「不知道写什么」时给灵感提示
> ③把每天 1 万多次免费额度真正用起来，而不是只用热榜那 1 次
>
> 状态：**待评审**。本文所有接口结论都来自 2026-10-19 的实跑探测，不是文档转述。
> 密钥已在本次会话通过环境变量验证可用，**但未写入本仓库任何文件**（详见 §7 安全）。

## 0. 已验证的事实（实跑探测结果）

四个接口全部 `HTTP 200`，凭证有效。真实返回结构如下：

### 0.1 鉴权

```http
GET https://developer.zhihu.com/api/v1/content/hot_list?Limit=2
Authorization: Bearer <access_secret>
X-Request-Timestamp: 1792418139     # 秒级 Unix 时间戳，必传，漏了直接被拒
Content-Type: application/json
```

### 0.2 知乎热榜 `GET /api/v1/content/hot_list?Limit=N`（Limit ≤ 30）

```json
{
  "Code": 0, "Message": "success",
  "Data": {
    "Total": 2,
    "Items": [{
      "Title": "如何评价……？",
      "Url": "https://www.zhihu.com/question/2094350166518249285?utm_medium=openapi_platform&utm_source=cf621feb3f2d",
      "ThumbnailUrl": "https://pic4.zhimg.com/v2-7b8f007b803849b3a270a38ada94844b.jpg",
      "Summary": "近日，……（约 200 字现成的事件摘要）"
    }]
  }
}
```

**三个关键观察（直接决定数据建模）：**

1. **没有热度值字段**。只有 `Title / Url / ThumbnailUrl / Summary`。想做「热度趋势」只能靠**排名随时间的变化序列**，不能指望平台给你热度分。
2. **`Url` 里有 question id**（`question/2094350166518249285`）。这是跨批次归并同一话题的唯一稳定键 —— 用 `utm_` 后面的追踪参数做 key 会炸（`$utm_source` 每个 secret 不同），必须裁掉 query string 再取 id。
3. **`Summary` 是免费的现成摘要**（约 200 字）。这是宝藏：拿它做选题判断零成本，不用再额外调 deeper 接口。

### 0.3 知乎搜索 `GET /api/v1/content/zhihu_search?Query=&Count=`（Count ≤ 10）

字段：`Title / ContentType(Article|Answer) / ContentID / AuthorSignature / ContentText / Url / CommentCount / VoteUpCount / AuthorName / AuthorAvatar / AuthorityLevel`

⚠️ **`ContentText` 返回的是正文全文**（实测一条就有几千字）。喂给 LLM 前必须截断（建议 600–800 字），否则一轮对话就烧掉几万 token。

### 0.4 全网搜索 `GET /api/v1/content/global_search?Query=&Count=`（Count ≤ 20）

返回结构与站内搜索一致。支持 `Filter` 参数：`host=="example.com" AND publish_time>=1778494631`。注意 `host` 不支持 zhihu.com 及其子域。

### 0.5 直答 `POST /v1/chat/completions`（**完全兼容 OpenAI 协议**）

```python
client = openai.OpenAI(
    api_key="<access_secret>",
    base_url="https://developer.zhihu.com/v1",
    default_headers={"X-Request-Timestamp": str(int(time.time()))},
)
client.chat.completions.create(model="zhida-fast-1p5", messages=[...])
```

三档模型：`zhida-fast-1p5`（快，日常够用）/ `zhida-thinking-1p5`（深度，返回 `reasoning_content` 推理过程）/ `zhida-agent`（检索增强，类 RAG）。支持 `stream: true`。

> **这条最有意思**：知乎对本项目而言不只是一个数据源，它同时是一个潜在的**第二模型供应商**（见 §5）。

### 0.6 尚未验证的能力

你给的日额度里还有这几项，我**没探测成功**（官方文档页 `developer.zhihu.com/docs` 需要登录，目录拿不到）：

| 能力 | 日额度 | 我的判断 |
|---|---|---|
| 问题发现 | 100 | 极可能是发现某领域下用户正在问的问题 —— **选题金矿**，优先级应高于热榜 |
| 创作能力 | 200 | 推测是让知乎侧生成内容，需确认版权与可用性 |
| 知识库 | 500 | 推测为检索增强类接口 |
| 小工具 | 10 | 只有 10 次，稀缺，务必先摸清再动 |

**处理方式**：实施第一步（P0）先用 MCP/官方 skill 清单把这些能力的真实调用签名摸出来，不在没验证的端上写业务代码。

## 1. 先纠正一个前提：每天一次太浪费了

你说「至少每天请求一次知乎热榜」——这是个安全但严重浪费的目标：

| | 每天一次 | 建议方案 |
|---|---|---|
| 热榜额度消耗 | 1 / 100（**1%**） | 12 / 100（每 2 小时一次） |
| 数据形态 | 单点快照 | **时间序列** |
| 能得到 | 今天榜上是啥 | 谁在爬升、谁是新上榜、谁死赖着不下榜 |

**为什么时间序列值钱得多**：单点快照只告诉你「现在什么热」，而做内容真正需要的是**变化率** —— 一个 2 小时内从第 28 名冲到第 6 名的话题，才是值得立刻下笔的选题；一个连续三天挂在 Top 10 的话题，说明是长线议题不急；一个刚上榜的，可能是明日热点。这些信号每天采样一次是**算不出来的**。

额度上也很宽松：每 2 小时一次 = 12 次/天，还剩 88 次给实时调用（用户随时点「刷一下热点」）和失败重试，绰绰有余。频率做成配置项，`HOT_FETCH_INTERVAL_HOURS` 随时调。

## 2. 数据模型设计（两张表，新表自动建不用改补丁清单）

> 好消息：项目是 `Base.metadata.create_all`，新模型只要在 `app/models/__init__.py` 注册导入就会自动建表，
> **不需要**动 `app/db/session.py` 的 `_SQLITE_COLUMN_PATCHES`（那玩意只负责给老表补列）。

```python
# app/models/zhihu.py

class HotSnapshot(Base):
    """一次抓取批次（审计用：知道哪次抓成功/失败/抓到多少条）"""
    __tablename__ = "zhihu_hot_snapshots"
    id: Mapped[str]              # uuid4().hex
    fetched_at: Mapped[int]       # Unix 秒
    item_count: Mapped[int]
    ok: Mapped[bool]
    error: Mapped[str | None]

class HotTopic(Base):
    """热点话题的每一次露面（一行 = 某话题在某时刻的排名）"""
    __tablename__ = "zhihu_hot_topics"
    id: Mapped[str]
    question_id: Mapped[str]      # 从 Url 解析出的稳定 id —— 归并键
    title: Mapped[str]
    url: Mapped[str]              # 存清洗过 query 的干净链接
    thumbnail_url: Mapped[str | None]
    summary: Mapped[str | None]   # 平台自带摘要，零成本选题素材
    rank: Mapped[int]             # 1-based 名次 —— 趋势全靠它
    snapshot_id: Mapped[str]
    fetched_at: Mapped[int]

    __table_args__ = (Index("ix_zhihu_hot_topic_qid_time", "question_id", "fetched_at"),)
```

**关键设计决策**：不建「话题主表 + 排名从表」，而是**每条榜单记录都单独存一行**（`HotTopic` 是「某话题在某时刻的一次露面」）。理由：SQLite 上做「同一 question_id 的历史最大/最小/最新排名」只要一个 `GROUP BY`，聚合是查询时才算的事；维护一张会被反复 UPSERT 的主表反而增加写入复杂度和锁冲突。表行数估算：30 条 × 12 次/天 = 360 行/天，一年 13 万行 —— SQLite 毫无压力。

**由此派生出的趋势信号（这才是选题金矿）：**

| 信号 | 算法 | 选题含义 |
|---|---|---|
| `is_new` | 该 question_id 最早出现时间 ≥ 今天 00:00 | 新上榜，抢首发 |
| `climb` | 本次 rank 与 2 小时前 rank 之差 | 正数越大越紧急，比如 +15 = 两小时冲了 15 名 |
| `staying_days` | question_id 最早出现距今的天数 | 长线议题，可以从容打磨 |
| `heat_score` | ` climbing 权重 × 0.6 + 高排名权重 × 0.4` | 综合排序喂给灵感卡片 |

## 3. 功能设计

### F1 热点抓取守护（满足诉求①）

挂uvicorn lifespan，不需要引入 APScheduler（项目现在没有任何调度框架，为一个定时任务上 Celery 太重）：

```python
# app/main.py:37-81 的 lifespan 里追加
task = asyncio.create_task(hot_fetch_loop())

async def hot_fetch_loop():
    await asyncio.sleep(30)                      # 让 init_db 先跑完
    while True:
        try:
            await fetch_hot_once()               # 见 app/services/zhihu.py
        except Exception as e:
            logger.warning("hot fetch failed: %s", e)   # 永不让它炸掉主循环
        await asyncio.sleep(HOT_FETCH_INTERVAL_HOURS * 3600)
```

失败处理三要点：①循环里吞掉所有异常，一个定时器不该拖垮服务 ②失败也要写一条 `ok=False` 的 snapshot，运维才有据可查 ③启动时先查「最近一次成功快照距今多久」，超过间隔就补抓一次 —— 休眠/重启后不会断档（这台沙箱就会休眠，这条很重要）。

### F2 对话页灵感注入（满足诉求②）

这是 UX 上的重头戏。不建议做的方案是**把所有热点塞进 system prompt** —— 污染上下文、每轮都烧钱、而且用户 90% 的对话根本不需要它。

推荐做三层，由轻到重：

**第 1 层：空白态灵感卡片**（零 LLM 成本，效果最直接）

新会话 / 无会话时，输入框上方展示一张卡片：

```
今天知乎在热什么（10-19 21:00 更新）
🔥 司美格鲁肽在美遭批量起诉，……        ↑15 位 · 2 小时冲上第 6
   这事爆得快，适合今天就出科普稿   [以此选题]
🔥 如何评价某某留学生事件……            🆕 新上榜
   争议类话题先定调再写，别蹭太急   [以此选题]
```

每条用平台的 `Summary` 直接展示，不需要 LLM 加工。点「以此选题」自动往输入框填一段 prompt：

```
请围绕下面这个知乎热点，为【小红书】生成一篇内容：
标题：……
摘要：……
切入建议：该话题 2 小时内热度上升 15 位，时效性强，建议尽快出稿。
```

**第 2 层：交流中兜底工具**（见 §4 `zhihu_hot_topics`）—— 用户直接问「今天写点啥」时，DeepSeek 自己调工具拿数据回答，比写死的前端逻辑灵活。

**第 3 层（可选）**：用户在输入框输入「不知道」「写啥」「没灵感」这类词时，轻推一下卡片。这层可以后做，优先级低。

**为什么不把推荐做成强打扰**：这个工作台是给人干活用的，创作者反感被喂稿。卡片可折叠、只在新会话出现 — 不会打扰已有思路的用户。

### F3 每日热点简报（直答 × 热点）

每天把 Top 8 热点丢给 `zhida-fast-1p5` 生成 100 字解读，组成「今日选题简报」：

- 消耗直答 8 次/天（额度 100，占 8%）
- 直答是知乎自家模型，解读知乎热点有天然数据优势（比 DeepSeek 更懂「知乎上大家在争什么」）
- 产物存在 `zhihu_daily_brief` 表或直接塞进灵感卡片顶部

## 4. AI 工具链接入（`app/tools/builtin.py` 现有 5 个工具）

新增 3 个**只读**工具，不需要 `TOOL_REQUIRE_CONFIRM`（那东西是给推送/渲染这类危险操作用的，搜索类只读工具加了 confirmation 只会拖慢创作节奏）：

| 工具 | 作用 | 消耗额度 |
|---|---|---|
| `zhihu_hot_topics(limit, sort_by)` | 今日热点 + 趋势信号（climb/new/staying） | 0（读本地库） |
| `zhihu_search(query, count)` | 站内素材检索，返回标题/摘要/赞同数/权威等级 | 5000/天池 |
| `global_search(query, count)` | 全网素材 + 事实核查（配合现有 `check_compliance`） | 5000/天池 |

实现要点：

- **喂给 LLM 前必须截断**：`ContentText` 全文几千字，工具返回给模型时截到 600 字并标注「（全文截断，原文链接：…）」
- **`AuthorityLevel`（权威等级）字段要利用起来**：搜索结果里带这个字段，过滤掉低权威来源后再喂模型，比只看赞同数靠谱
- 工具注册照现有范式：`app/tools/registry.py` 的装饰器 + `main.py:34` 导入生效

⚠️ **一个必须提前说的约束**：`app/services/agent.py:124-131` 和 `llm.py:362-364` 有逻辑 —— **`provider=cloudflare` 时强制 `tools=None`**。也就是说，如果用户在个人中心把对话通道切到 Cloudflare，这三个知乎工具会集体失效。实施方式：要么在工具不可用时前端提示「知乎工具需 DeepSeek 通道」，要么干脆做成后端始终用 DeepSeek 的旁路。这个得你来定，两种都合理。

### 一个额外想法：知乎不止是数据源，还可以是第二个模型供应商

直答完全兼容 OpenAI 协议（已实测通过），而项目本来就有 provider 切换机制（`app/services/llm.py`）。把 `zhida` 加成第三个 provider 成本很低。

但**别把它当主力对话模型** —— 直答 100 次/天，正常聊天几轮就用完了。它合理的定位是**按问题类型路由**：

- 问知乎生态、知乎热点、中文领域的争论性问题 → 走直答（它有知乎数据，比 DeepSeek 懂「知乎上大家在争什么」）
- 其他创作任务 → 走 DeepSeek

具体实现可以做成「人肉切换」（个人中心已有的 AI 对话选项里多一项）而非自动路由 —— 自动路由需要判断意图，成本高、易误判，且用户现在也不确定想不想让你替他选模型。**这条我标为可选，等你拍板。**

## 7. 风险与约束（必须提前知道）

1. **🔴 密钥安全 —— 最重要的一条**。`Access Secret` 持有完整 API 权限，且**同一账号下所有 secret 共享同一个额度池**。绝不能出现在前端代码、git 提交、日志文件里。放 `.env`（项目 `.env` 已在 `.gitignore`，安全）。这次探测我是用**环境变量**跑的，没有落盘到仓库任何文件 —— 建议你也别在任何聊天窗口或文档里贴完整值。
2. **Cloudflare 通道下工具失效**（§4 已述）。
3. **限流**：热榜高频调用会触发错误码 `30001`。2 小时间隔很安全，实时查询要加最短间隔保护（比如同一用户 60 秒内不重复请求 API，读库不限）。
4. **单次上限**：搜索 Count≤10、全网≤20、热榜 Limit≤30 —— 想多拿只能多次翻页/多次调用。
5. **内容版权**：知乎内容是他人创作，开放平台明确要求**内容溯源**。方案里的用法（给创作者提供选题灵感 + 素材参考）是安全的，**但直接搬运 `ContentText` 成稿发布不行**。生成内容时建议保留来源链接。
6. **休眠断档**：这台沙箱会休眠，容器起来后服务要重挂 —— 所以 F1 必须有「启动补抓」逻辑。
7. **额度池共享**：你在开放平台的页面测试调用也扣同一个池。对账要以个人中心实时用量为准。
