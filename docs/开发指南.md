## 声音复刻：本地零成本路线

> 默认不需要看这一节。开箱状态 `VC_PROVIDER=edge`，配音走 edge-tts 官方音色，零额外依赖。
> 只有想「用自己录的声音念稿」时才按下面装，装完把 `.env` 的 `VC_PROVIDER` 改成 `xtts`。
> 项目同时支持 `cloud`（云端 API，效果最好、要花钱），配置见 `.env.example` 的声音复刻段注释。

### 它到底在做什么

XTTS-v2 是**零样本**声音克隆：给一段 10~30 秒的参考录音，当场就能合成，**不用训练、不用 GPU、不用保存权重**。项目里那个「提取音色」的过程（`XttsProvider.train()`）本质是**预热**——把模型加载进内存、算一次 reference embedding 缓存起来，目的是把几十秒的模型加载时间从「每次渲染」挪到「只做一次」。

复刻出来的音色在接口上伪装成一个普通音色名，形如 `clone_<profile_id>`（`profile_id` 是音频内容的 md5 前 12 位，同一段录音重复上传命中同一条，不会出现三个一模一样的「我的音色」）。渲染管线 `video_pipeline.synth_voice()` 只在门口加了一个 `is_clone_voice()` 分支，后面 400 行一行没动。

### 安装（版本必须按这个组合装）

```bash
cd backend

# 1) torch 三件套走官方 CPU 源（别从 PyPI 装，会拉 CUDA 版多出 2GB+）
uv pip install --system torch==2.9.1 torchaudio==2.9.1 torchvision==0.24.1 \
    --index-url https://download.pytorch.org/whl/cpu

# 2) 其余依赖走清华源
uv pip install --system coqui-tts==0.27.5 "transformers==4.57.6" \
    "numpy==2.2.6" soundfile==0.13.1 pypinyin==0.55.0 jieba==0.42.1 torchcodec==0.17.0
```

**为什么版本卡这么死**（每条都真实踩过，别自作主张升级）：

| 约束 | 症状 | 原因 |
|---|---|---|
| `transformers<5` | `ImportError: cannot import name 'isin_mps_friendly'` | 5.x 删了 TTS 依赖的这个符号 |
| torchvision 与 torch minor 对齐 | `operator torchvision::nms does not exist` → 连锁 `Could not import module 'GPT2PreTrainedModel'` | 0.25.0 配 torch 2.9.1 不匹配，transformers 惰性导入崩 |
| `numpy<2.3` | `Numba needs NumPy 2.3 or less` | librosa → numba 链 |
| 装了 `torchcodec` 但仍用 soundfile | `undefined symbol: torch_list_size` / `torch_from_blob` | 见下 |

**torchcodec 这段是整节最绕的坑**：从 torchaudio 2.9 起，`torchaudio.load/save/info` 的实现改为委托 torchcodec；而 torchcodec 的原生 `.so` 按特定 libtorch ABI 编译，实测 0.7.0 / 0.17.0 全都对不上当前 torch（`nm -D` 搜遍所有 torch 库都找不到它要的符号，属于 torchcodec 自身发布节奏问题，**版本对齐这条路走不通**）。

解法在 `backend/app/core/audio_compat.py`：模块被 import 时在运行时把 `torchaudio.load/save/info` 替换成 **soundfile** 实现（契约等价，注意 soundfile 返回 `(samples, channels)` 要转置成 torchaudio 约定的 `(channels, samples)` float32）。选运行时补丁而不是改 TTS 源码，是因为 TTS 有 5 个文件要改、`pip install -U` 一升级就冲掉，很容易改坏（我第一次改就把 `xtts.py` 的多行 import 括号块改出 SyntaxError，最后只能 `--force-reinstall` 重装）。`voices.py` 顶部那句 `from app.core import audio_compat  # noqa: F401` 就是这个补丁的开关，**别删**。

### 首次运行要下模型（约 1.9GB）

XTTS-v2 模型权重第一次用才会下，落在 `~/.local/share/tts/tts_models--multilingual--multi-dataset--xtts_v2/`。

国内网络注意：TTS 的 `.models.json` 里 `hf_url` **写死了 huggingface.co 域名**，`HF_ENDPOINT` 环境变量对它无效。huggingface.co 不通时要手工下：

```bash
# 从 TTS 包里读出该模型的文件清单，逐个用国内镜像下
python -c "import json,pathlib,TTS; p=pathlib.Path(TTS.__file__).parent/'.models.json'; \
  d=json.load(open(p))['tts_models/multilingual/multi-dataset/xtts_v2']; print(list(d.keys()))"
# 逐个（共 5 个）：config.json / vocab.json / hash.md5 / speakers_xtts.pth / model.pth
curl -L -o <目标目录>/<文件名> \
  https://hf-mirror.com/coqui/XTTS-v2/resolve/main/<文件名>
```

镜像有 5 分钟 100000 次请求的限流，碰到返回 317 字节的错误页就 `sleep 45` 再重试，直到文件大小正常（`model.pth` 约 1.87GB，`speakers_xtts.pth` 约 7.75MB）。

### 录音怎么录才像

上传的录音会被强制过一遍 ffmpeg 清洗（`voices.py: normalize_reference()`），四步：单声道 24kHz 重采样 → `highpass=f=60` 滤低频嗡声 → 首尾静音裁剪（只裁首尾，不动中间停顿）→ `loudnorm=I=-18:TP=-2:LRA=11` 响度归一。

**XTTS 会把参考音频的噪声一起复刻**，所以这一步比选哪条路线影响更大。给用户的录音建议：安静环境、离麦 15~20cm、正常语速连续说 15~30 秒、别有背景音乐。质量评级由 `_fingerprint()`（时长/RMS/过零率/峰值）+ `quality_hint()` 给出 `ok`/`warn`/`bad` 与中文建议（太短 / 太轻 / 削波失真）。

### 渲染时的时间轴

edge-tts 会返回 SentenceBoundary（带时间戳），但 **XTTS 和云端 API 都不返回**。所以复刻音色合成时会把文本切成 ≤80 字的短段（`_TTS_CHUNK_CHARS`）逐段合成，再用 ffprobe 实测每段时长累加回算出字幕轴（`_concat_segments()`）。段长漂移较大，但短段同时能避免 XTTS 长文本「念到后面音色跑偏」。

模型在进程内是单例（`_xtts_cache`，常驻约 1.8GB 内存），每请求重载会把 30 秒视频卡成 3 分钟且容易 OOM；CPU 密集的合成走 `asyncio.to_thread` + `asyncio.Semaphore(1)` 串行。

### 复刻音色渲染到底有多慢（别误判成卡死）

**实测数据**（16 页讲义、3798 字）：XTTS 在 CPU 上**平均约 42 秒合成一段**，41 段花了 29 分钟。
按 3798 字 / 每段 ≤80 字估算，总段数约 **130~150 段**，整条渲染要 **1.5~2 小时**。

**所以进度条长时间不动是正常的**——不是卡死。判断方法：看 workdir 里 `clone_seg_NNN.wav` 有没有在增长：

```bash
ls -lt backend/data/outputs/work_<job_id>/clone_seg_*.wav | head -3
```

文件时间戳在往前推 = 正常干活。

> **⚠️ 但只数文件会误判**：沙箱休眠重启后，渲染进程会消失，而文件数是历史遗留的。
> **必须交叉验证进程还在**：
> ```bash
> uptime                            # 明显短于操作时长 = 沙箱重启过
> ps aux | grep uvicorn             # 后端在不在
> ss -tlnp | grep 8000              # 端口有没有在听
> ```
> 实测 2026-10-15：任务跑到 113 段时沙箱静默重启，进程全没、站点 502，
> 但文件数仍在（滞后信息），差点误报「还在正常渲染」。恢复：
> `bash deploy/install-autostart.sh`。

为了不让用户干等，`voices.py` 里做了两层进度兜底：

1. **逐段上报**：`synth()` 每合成完一段回调 `on_progress(5 + int(25*(i+1)/n), "正在合成配音 i/n")`，把 5%~30% 这段区间填满。
2. **心跳兜底**：`_progress_heartbeat()` 在模型预热（`train()`）阶段用 `1 - 1/(1+t/3)` 收敛曲线把 40%~92% 平滑爬升，即使上一段还没出，进度条也在动。

> **踩坑**：进度回调可能来自 `asyncio.to_thread` 的**子线程**，子线程里没有默认事件循环，
> `asyncio.get_event_loop()` 会直接抛异常。必须用 `asyncio.get_running_loop()` +
> `loop.call_soon_threadsafe()` 调度回主循环。`render.py` 里还加了进度去重
> （`p <= last` 直接 return），否则上百段会写上百次库。

## 如何加一个新工具

以「生成配图」为例：

```python
# backend/app/tools/builtin.py
@tool(
    name="gen_cover_image",
    description="根据文案主题生成封面图，返回图片 URL",
    requires_confirm=False,          # 只生成不发布，无需确认
    timeout=60,
)
async def gen_cover_image(topic: str, style: str = "clean") -> dict:
    # 调外部 API 或本地模型……
    return {"ok": True, "url": "https://..." }
```

完事。`registry.openapi_schemas()` 会自动把它喂给模型，前端工具轨迹自动渲染。

**什么时候要 `requires_confirm=True`**：任何影响外部系统状态的操作（发布、推送、删除、花钱）。确认名单同时要在 `.env` 的 `TOOL_REQUIRE_CONFIRM` 里登记——`/api/chat/confirm` 会双重校验。

## 如何加一个新排版主题

主题是**纯资产增量**，不用改 Python 逻辑（除了登记一行）：

1. 在 `backend/app/assets/gzh/` 新建 `theme-{英文标识}.md`，**必须含五部分**（照抄现成主题的结构即可）：设计变量速查表 / 各组件完整 HTML / 完整文章模板骨架 / 文章类型→组件组合配方表 / Markdown→组件映射规则表。所有 HTML 遵守平台红线：内联 style、文字 `<span leaf="">` 包裹、禁 `<div>`/`class`/`position`/`@media`。
2. `backend/app/assets/gzh/themes.py` 的 `THEMES` 加一条（`id`/`name`/`color`/`scenes`/`desc`）——**文件名 `theme-{id}.md` 的 `{id}` 必须与这里的 key 一致**，前端下拉自动出现。
3. `backend/app/assets/gzh/theme-index.md` 表格补一行（「正文下划线 CSS」列是该主题下划线色值的权威来源）。
4. 自检：用 `validate_gzh_html()` 过一遍 md 里所有 ```html 代码块（0 ERROR），再真实排版一次看效果。
5. **重启后端**（`THEMES` 是模块级常量、`load_theme_lib` 带 `lru_cache`，热改不生效；这就是坑 43）。

> 品牌方给的 PNG 素材（分隔符/引导卡/章节条等）**要用内联 HTML 复现成组件**，不要直接当图片塞正文——PNG 在公众号里不能随内容自适应、也无法覆盖不同文案。参考 `theme-mashang-liaoliao.md`：渐变条用 `<section>`+`linear-gradient`、品牌气泡用内联 `<svg>`、装饰空元素带 `<span leaf=""><br></span>`。

## 如何加一个后台定时任务

以知乎热榜抓取（`services/zhihu.py` 的 `loop_hot_fetch`）为例，四条纪律：

1. **挂 lifespan**：`main.py` 的 lifespan 里 `asyncio.create_task(loop_xxx())`，不要用 APScheduler——多一个依赖多一处版本坑，`asyncio` 足够；
2. **循环体内吞掉一切异常**：一个定时任务没资格把服务拖垮，`while True` 里包 `try/except` + 日志；
3. **启动先补抓**：先查「上次成功是什么时候」，超间隔就立刻补一次。这台沙箱会休眠，不补的话每次唤醒都要空等一个间隔才有数据；
4. **没配凭证就安静退出**：`if not _configured(): return`，不刷日志、不占资源。

抓取类任务还要记**批次审计**（成功/失败都写一条），否则漏采了无从发现；有外部额度的任务加**水位保护**（见 `usage_today()`），超了写失败快照并跳过，别裸奔。

## 已知坑（都踩过，别再踩）

1. **`python3` 与 `pip3` 不一致**：本机 pyenv 场景下用 `python3 -m pip install`，别用裸 `pip3`。
2. **模型导入顺序**：`Base.metadata.create_all` 只认已 import 的模型。`app/models/__init__.py` 已聚合导出，新模型文件记得在 `__init__.py` 里加一行 import，否则表建不出来（报 no such table）。
3. **SQLite 目录不存在**：`session.py` 的 `_ensure_sqlite_dir()` 会在建 engine 前自动建目录；换 DATABASE_URL 路径时无需手动 mkdir。
4. **Vue 里 `h` 被遮蔽**：从 vue 导入的渲染函数 `h` 极易被局部变量（如 `const [h, t] = await ...`）遮蔽，症状是表格只渲染表头、控制台一堆渲染错误。局部变量换名。
5. **Naive UI 的 `NTable` 不可靠**：渲染函数列定义请用 `NDataTable`，`NTable` 配 render 会静默丢行。
6. **health 双路径**：前端 axios baseURL 是 `/api`，Vite 代理只转 `/api/*`。裸 `/health` 给探针用，`/api/health` 给前端用，两个都要存在。
7. **中文引号**：Python 字符串里写 `"` `"}` 会直接语法错误，中文文案里的引用用 `『』`。
8. **`EventSource` 只支持 GET**：对话流是 POST，必须 `fetch + ReadableStream` 手动解析 SSE（见 `api/chat.ts`）。
9. **Prompt Cache 一改就失效**：`prompts/platforms.py` 的措辞是计费缓存的一部分，小改一次 = 全量重算一次输入价。调整提示词请集中批量改。
10. **移动端内容区防遮挡**：底导是 fixed 定位，内容区 padding-bottom 必须是 `calc(76px + env(safe-area-inset-bottom))`，否则 iPhone 全面屏下最后一行被遮。
11. **pnpm 版本必须锁 10.x**：pnpm 12 默认开启 `minimumReleaseAge`（24 小时），把刚发布的依赖判为「太新」而拒绝 `--frozen-lockfile`。`package.json` 已声明 `packageManager: pnpm@10.28.2`，`frontend/.npmrc` 里也设了 `minimumReleaseAge=0`，别删。
12. **nginx 里 `proxy_buffering off` 不能删**：这是 SSE 流式输出的命门。开着缓冲的话，AI 的回答会攒成一整段才吐给浏览器，逐字显示的效果就没了。同时 `proxy_read_timeout` 要给够（配了 300s）。
13. **`Cannot find module @rollup/rollup-linux-x64-gnu`**：pnpm 在部分场景下会漏装 rollup 的平台原生二进制（可选依赖的老问题）。症状是 `pnpm dev` 直接崩。解法就一句：`rm -rf node_modules && pnpm install`，装完确认 `node_modules/.pnpm/` 下有 `@rollup+rollup-linux-x64-gnu@*`。别去动 `.npmrc` 或锁文件。
14. **流式 usage 挂在有 choices 的 chunk 上**：DeepSeek 开 `include_usage` 后，带 usage 的收尾 chunk **仍有 1 条 choices**（finish_reason=stop），不是 `choices=[]`。在 `if not chunk.choices: continue` 之后才查 usage 的写法会静默丢掉全部用量统计。必须在 choices 判空**之前**每轮都查 `chunk.usage`。
15. **推理模型两个输出通道**：`deepseek-flash` / `deepseek-v4-pro` 先流 `reasoning_content`（思维链）再流 `content`（正文），是两个独立字段，绝不能拼接混用。且思维链 token 计入 `max_tokens`——写 800 字文章实测要烧 1100-2000 思维链 token，`max_tokens` 给 4096 会把正文挤成截断或空串。现配 16384/32768。
16. **模型会重复调同一个工具**：长上下文里模型容易忘了自己刚调过什么，实测 3 条小红书标题触发 10 次 `check_compliance`，撞上 `MAX_TOOL_ROUNDS` 被中止。双层防御：① 系统提示里写明工具使用纪律（`prompts/platforms.py`）；② `agent.py` 按「工具名+参数」指纹缓存执行结果，完全相同的重复调用直接回放缓存并提醒模型。改工具参数语义时记得同步指纹逻辑。
17. **复刻音色不在 edge-tts 清单里**：`/api/video/render` 提交时的音色校验原本只比 `valid_voices()`（edge-tts 官方清单），复刻音色必然被判「音色不可用」。已改成双分支：`is_clone_voice(voice)` 为真时只校验音色库里有没有这条 profile，否则才走官方清单。**以后再加新的音色来源，记得同步这处校验**。
18. **`audio_compat.py` 的 import 不能删**：它是 torchaudio → soundfile 运行时补丁的开关，删了会在第一次合成时炸 `undefined symbol`。另外 `_xtts_cache` 里缓存的参考音频 `profile_dir/reference.wav` 每次合成都要重读，**不能**像其它中间产物那样合成完就删。
19. **别在同库上起第二个实例做验证**：`recover_orphans()` 启动时会把所有 `running` 任务标成 `failed`（假设是上次崩溃遗留）。拿别库验证会出事——实测用 `uvicorn --port 8899` 起第二个进程连**同一个 SQLite**，直接把主进程正在跑了 50 分钟的任务标成了失败（工作其实还在继续，只是状态被改坏）。现已加 `flock` 实例锁（`/tmp/cwb-render.lock`）：拿不到锁的实例跳过孤儿清理。**要起第二个实例验证，务必换 `DATABASE_URL` 或设 `RENDER_LOCK_FILE` 指向别处**，或干脆别起（本任务类型直接 `curl` 主实例即可）。
20. **长任务轮询别用完整接口**：完整 `/video/jobs/{id}` 响应 22KB，经 Cloudflare Tunnel 单次 1.7~2.9 秒。轮询走 `/video/jobs/{id}/progress`（267 字节）。另注意 `JobProgress` 在 `frontend/src/api/tools.ts` 里刻意定义成 `Pick<RenderJob, ...>` 子集，`upsertHistory` 也改成按字段合并 —— 别改回整条替换，否则轮询会把列表项里的 script 冲掉。
21. **nginx 的 `client_max_body_size` 必须显式配**：nginx 默认 **1MB**，手机录音（几十秒的 m4a/mp3）轻松超过，表现是**上传直接 413，前端白屏**。项目自带的 `deploy/nginx.conf` 里有 `60m`，但服务器上 `/etc/nginx/sites-available/cwb` 是手写的、漏了这行 —— 实测 2026-10-15 手机端上传全部失败就是这个原因。已补上，**换服务器/重建 nginx 配置时记得检查这行**。
22. **知识库素材不能拼进 system_prompt 字符串**：`strip_tool_discipline()` 会从「工具使用纪律」标记一刀切，拼在后面的素材在 CF 通道被整段丢弃。必须走 `build_context()` 的独立 system 消息（见 `services/conversation.py::KNOWLEDGE_HEADER`）。
23. **关键词降级阈值别复用余弦阈值**：余弦 0.45 的门槛对「query 二字组命中比例」是灾难（10 个二字组命中 3 个才 0.3），会把降级结果全误杀。按「命中个数」卡（`KB_MIN_KEYWORD_HITS`），见 `services/knowledge.py::_keyword_search`。
24. **动态工具的 enum 不能写死**：`activate_skill` 的 `name` 必须按 owner 实时算 enum（`dynamic_tool` + `registry.schemas_for(ctx)`）。写死或复用 `registry.schemas()` 会有两个坑：① 把 A 用户的技能名发给 B 用户的模型；② 没有技能时发出一个空 enum 工具，模型会反复试错。**没有可用技能时整个工具不出现**是刻意的，不是 bug。
25. **技能导入失败不能覆盖同名的可用版本**：先传对了再传坏文件，好技能会被打成 invalid 且无法撤销（2026-10-22 实测）。`upsert_skill` 在「同名已有 ready 版本」时改为抛 `SkillParseError` 由路由转 400。改这块前先看 `tests/test_skill.py::test_broken_import_does_not_clobber_good_version`。
22. **同一音色 id 的复刻必须串行**：`create_profile` 用**音频内容 MD5 前 12 位**做 profile_id（重复上传同一录音命中同一 id，避免列表里出现多个一模一样的音色）。但同一 id 的多次复刻会**共享同一目录**，并发跑会互相删掉对方的 `reference_raw` / `reference.wav` —— 症状是音色出现在列表里、可试听接口 404、渲染时找不到参考音频。已在 `clone_voice()` 外层加 `_clone_locks`（每 profile 一把 `asyncio.Lock`）串行化解决。

    **最典型的触发场景：用户把同一段录音传了两次**（手滑、或以为没传成功又传一次）。两次上传命中同一 id（这是设计的正常行为，目的是不产生重复音色），但两次复刻并发跑就把文件踩坏了。已修复并实测验证：连传两次 → 目录 `meta.json` + `reference.wav` + `voice.json` 全部完整，试听 200，列表里只出现 1 条。
23. **测上传别用固定的小音频反复传**：内容哈希做 id 意味着你反复上传同一份测试文件会命中同一个 id 并互相覆盖，还会跟真实用户的并发上传撞车（2026-10-15 真踩过：我用固定测试音频连传 3 次，正好把用户手机上传的那次复刻数据踩坏，害得用户以为"上传了但没音色"）。**要验证就每次生成不同内容的音频**（`ffmpeg -f lavfi -i "sine=frequency=<换个值>:duration=25"`），验证完删掉。
24. **本机 ffmpeg 是 `--disable-libx264` 的构建**：沙箱里的 ffmpeg 只带 `libopenh264`（无 `libx264`/`libx265`），项目代码里 `VIDEO_CODEC = "libopenh264"` 就是为此。**自己写测试命令时别顺手写 `-c:v libx264`**，会报 `Unknown encoder 'libx264'`；要么用 `VIDEO_CODEC`，要么 `-c:v libopenh264`。
25. **口播稿字幕走的是 `mov_text` 软字幕轨，别做成硬字幕（烧进像素）**：需求是「口播稿当字幕，但 PPT 每页画面原封不动」。用 `-c:s mov_text` 封成 mp4 第二条流即可（可开关、可导出），**不要**用 `subtitles=` 滤镜烧字。另外 `build_srt()` 给的是**句级**时间轴（`Scene.start/end` 本来就来自配音实测时长），不是字级 —— XTTS 不返回字级时间戳，硬做字级只能估算，没必要。`concat_clips()` 里 copy 与 filter 两条降级路径都带字幕轨，改动时别只顾一条。
26. **公众号 HTML 里所有文字必须包在 `<span leaf="">` 里**：公众号粘贴时只保留白名单标签 + 内联样式，纯文本节点没被 `<span leaf="">` 包住的话，**整段样式会成片丢失**（不是丢一点，是整片）。这是排版引擎最硬的契约，`services/gzh_validate.py` 专门数了 `span_leaf_count` 兜底。改排版 prompt 或主题模板时，凡是新增文字节点，先确认它被 `<span leaf="">` 包住。校验器还有 14 条禁用正则（`<div>` / `class` / `id` / `@media` / `var(--x)` / `position` / `float` 等），LLM 装配后必过一遍，有 ERROR 自动回修（≤2 轮）。
27. **`save_content` 已改 `requires_confirm=True` 且不再入队**：对话侧从 2026-10-16 起只产出纯内容，**模型不得主动入队**。入队的唯一入口是前端「保存到队列」→ `POST /api/content/items`（JSON body，队列项 `status=draft`）。别再把它改回「模型可自由调用 + 自动建 QueueItem」，那正是之前「用户不知道队列里怎么多了东西」的根因。`push_wechat_draft` / `render_video` 仍在确认名单，`.env` 的 `TOOL_REQUIRE_CONFIRM` 要同步登记。
28. **`IMAGE_SCRIPT` 的调用契约 + 未配置时的降级**：配图走本地生图脚本，后端以子进程方式调 `python <IMAGE_SCRIPT> --prompt <P> --size <S> --count <N> --out <DIR>`，然后取该目录下**新增的**文件当产物（调用前先快照目录文件做差集），文件名从 stdout 兜底解析。三个约束：① `IMAGE_SCRIPT` 为空或文件不存在 → `configured()` 返回 false，`/images/generate` 返回 **400 + 友好中文提示**（前端据此禁用生图按钮、引导手动上传），不会 500；② 超时由 `IMAGE_SCRIPT_TIMEOUT`（默认 180s）控制；③ 接入新脚本时先确认它认这套 CLI 参数，不认识就改 `imagegen.py:_run_script()` 的拼装。
29. **SQLite 加列靠 `_SQLITE_COLUMN_PATCHES`，不是 `create_all`**：项目没有 Alembic，`Base.metadata.create_all` **只建新表，不给已存在的表加列**——模型里加了字段但库已存在时，查询会报 `no such column`。`db/session.py` 的 `_SQLITE_COLUMN_PATCHES` 用 `PRAGMA table_info` 检测缺列后 `ALTER TABLE ADD COLUMN` 补上。**给 `Content`（或任何已上线表）加字段时，除了改模型，务必在 `_SQLITE_COLUMN_PATCHES` 里登记一行**（列名 → SQLite DDL），否则开发库原地炸。注意它只加列、不改类型、不删列。
30. **排版接口必须是「提交任务 + 轮询」，别改回同步**：公众号排版单次约 **2~3 分钟**（pro 模型装配 + 校验回修），而前端 axios 全局 `timeout` 只有 60s。同步的话前端必然超时（现象：一直转圈然后报错），而后端还在跑 —— 用户过一会儿打开发现已排好，以为「诈尸」。所以 `POST /content/items/{id}/layout` 只 `submit_layout_job()` 秒回 `task_id`，前端轮询 `GET .../layout/{task_id}`。任务表 `_LAYOUT_JOBS` 放**进程内存**（排版幂等，重启丢任务让用户重跑即可，成本只是一次 LLM 调用），`_LAYOUT_LOCK` 是 `Semaphore(1)` 串行排版防并发烧 token。轮询遇到 **404 = 任务已中断**，前端要提示「重新排版」而非报错。
31. **排版后台协程必须自建 Session**：`_run_layout_job()` 里用的是 `SessionLocal()`，**不能**复用请求期的 `db` —— 请求早就返回了，那个 session 已经关了。改动这块时特别容易顺手把 `db` 传进去，结果是任务一跑就 `Session is closed`。
32. **微信 IP 白名单要填「微信实际出网 IP」，不是 SSH 隧道服务器 IP**：后端调 `api.weixin.qq.com` 是从它所在机器出网的，微信只认这个出网 IP。项目里的 SSH 反向隧道（`deploy/tunnel-guard.sh`，远端 `49.233.223.252:18080`）只把公网访问**转发进来**，**不承载后端出网流量**，所以填它一点用没有。两个坑：① 沙箱/云主机出网 IP 可能是**动态**的（详见坑 51）；② 验证时若微信报 `errcode=40164`，就是 IP 不在白名单。**长期稳定的解法见坑 51**：用 `deploy/proxy-guard.sh` + `WECHAT_PROXY` 让微信请求固定从一台机器出网，白名单只填那 1 个 IP。设置页「测试连通」返回的 `egress.ip` 就是当前实际出口。
33. **公众号凭证支持「多号 + 默认号 + .env 回退」，优先级别搞反**：`wechat_accounts` 表存多号，解析顺序是「显式 `account_id` → `is_default=True` → `.env` 的 `WECHAT_APPID/SECRET`」（见 `tools/builtin.py:_resolve_wechat_client`）。**secret 一律不回传明文**，接口只给 `secret_set` 布尔；`PUT` 时 secret 留空 = 不改。加号/改号记得 `verified_at` 要作废（换了密钥旧验证无效）。token 缓存 key 是 `wechat:token:{appid}`，多号天然隔离，别改成全局 key。
34. **加工中状态用独立的 `Content.processing`，别塞进 `QueueItem.status`**：`status` 只管发布生命周期（draft/ready/published/archived），`processing` 管「正在做什么」（`""`/`layout`/`image`）。把 processing 塞进 status 会污染所有状态筛选/统计/跳转逻辑。队列页靠 `QueueItemOut.processing`（在 `queue.py:list_items` 里按 content_id 批量回填，避免 N+1）显示「排版中/生图中」并禁用操作。worker 里置位后**必须 try/finally 清位**，否则队列页会一直卡在「排版中」。
35. **SVG 的 presentation attribute 不认 `var()`**：`fill="var(--app-primary)"` 写成**属性**是无效的（SVG 属性不是 CSS），必须走 `:style="{ fill: 'var(--app-primary)' }"` 绑定。UsageView 的图表（堆叠柱/折线/条形图，含 `stop-color`/`stroke`/`fill`）全部这样改造过。给 SVG 上主题色时直接写 `:style`，别先写属性再怀疑人生。
36. **iframe `srcdoc` 是独立文档，不继承父页面的 CSS 变量**：公众号文章预览（LayoutPanel）走 `srcdoc`，里面的 `var(--app-text-3)` 全部失效，而且公众号文章**恒为白底**（粘贴到微信就是这个效果）。预览相关样式保持字面色（如占位文案 `#999`），不要试图让预览跟随 app 主题——那反而偏离真实粘贴效果。
37. **Naive UI 的 `--n-*` 变量不能在自己的 scoped 样式里用**：那些变量由各组件的 cssr 定义在**组件根元素**上，自有 scoped 样式不一定继承得到（时灵时不灵）。所以项目自建 `--app-*` 语义变量体系（`styles/theme.css`，`:root` 暗色 + `:root[data-theme='light']` 亮色），组件主题另走 `App.vue` 的 `:theme` + `GlobalThemeOverrides` 两条腿。**防首屏闪主题**靠 `index.html` 挂载前的同步内联脚本先设 `<html data-theme>`，改这块时别把内联脚本删了。
38. **浏览器直链带不了请求头，用 HMAC 签名而不是 `?owner=`**：`<img>` / `<audio>` / `<video>` 的 `src` 是浏览器直连，没法带头部。用户模块上线后，成片 URL、配图 URL、试听 URL、二维码 URL、幻灯片图 URL 全部由**服务端**拼 HMAC 签名（`security.link_url()`：`?o=<uid>&sig=<hmac(secret, owner+"\n"+path)[:32]>`，六处生成点：`layout.py` / `settings.py` / `services/layout.py` / `render.py` / `voice_clone.py`）。**别退回 `?owner=` 客户端自称，也别把 JWT 放进 URL**（全账户凭证进 Referer/历史，且过期=存量 URL 集体失效）。新增任何静态服务端点时，记得：① 加 `Depends(link_auth)`（签名优先、Bearer 兜底、都没有 404）；② 返回的 URL 走 `link_url()`；③ 文件路径按 owner 隔离时校验格式（防 `../` 穿越）。
39. **给端点加 owner 依赖时，单行签名的函数会被批量替换漏掉**：`def foo(...) -> X:` 写成单行（无尾逗号、无多行参数）时，按多行模式批量加依赖的脚本匹配不上它——实测 `queue.py` 的 `stats` / `export_markdown` / `get_content` 三个端点漏改，运行时报 `NameError: name 'owner' is not defined`。批量改完用 AST 扫一遍：**函数体里用了 `owner` 但签名里没有对应依赖**的，全部揪出来。（2026-10 用户模块落地时 53 处 `current_owner` → `current_owner_id` 就是这么批量改的，sed 后按 import 计数核对过：7 文件 × import + 53 处调用，一个不多一个不少。）音色目录还有个对应坑：克隆任务 key 是 `f"{owner}:{profile_id}"`（profile_id 是音频 MD5，两人上传同一段音频会撞 id）。
40. **封面与文内配图是两条通道，参数契约不同，别互相复用**：`make-cover.py` 认的是 `--title/--sub/--tag/--style/--size/--out`，而 `imagegen.py` 认 `--prompt/--size/--count/--out`。把封面脚本填进 `IMAGE_SCRIPT` 会因参数不匹配**直接失败**（脚本会报 unrecognized arguments）。正确做法：封面填 `COVER_SCRIPT`，走 `services/covers.py`；两者**都依赖本机有 Chrome/Chromium**（封面是 HTML 截图），沙箱里是 `/usr/bin/chromium`。
41. **封面脚本不能写死 Windows 路径**：原始脚本里 `BASE`/`CHROME` 是 `C:/Users/Admin/...` 的绝对路径，换到 Linux 直接拿到 `C:\...` 报错。已改成：`BASE = 脚本自身目录`、`CHROME` 自动探测（`COVER_CHROME` 环境变量 → 常见绝对路径 → `PATH` 里的命令名）、渲染加 `--no-sandbox`（容器内 root 必需）、输出目录由 `--out` 决定。**要改封面风格/配色，改 `backend/scripts/make-cover.py` 的 `BRAND` / `STYLES` 字典即可**，不用碰后端。
42. **封面在 `images` 里的位置就是语义**：封面固定占 index 1（列表首位，`source="cover"`），所以 LLM 留的 `<!--IMG:1-->` 天然指向封面。`_image_manifest()` 会把第一张标成【封面/头图】并在 prompt 里要求放正文最前。**改动配图相关逻辑时别把封面从队首挪走**，否则 `<!--IMG:1-->` 会指向别的图。重复调 `/covers/generate` 是「换封面」（旧文件自动清），不是追加。
43. **改了后端代码，务必确认常驻进程已重启**：本沙箱的 uvicorn 由守护进程（PPID 61）托管，`kill` 后会自动拉起**新**进程加载新代码；但如果只是改了文件没重启，旧进程仍跑旧代码。实测踩过：`_ensure_cover` 里 `Path` 未导入的修复已落盘，但排版时仍报 `name 'Path' is not defined`——因为进程启动时间（13:30:54）早于文件修改时间（13:31:35）。**排查「代码改了却不生效」先比 `ps -o lstart` 与文件 `mtime`**，别怀疑逻辑。
44. **naive-ui 组件没 import 会「静默塌成 0×0」，比报错更难查**：`ImageManager.vue` 里写 `<NDivider>` 却漏了在 `import { ... } from 'naive-ui'` 里加 `NDivider`，Vue 会把它当成**未注册的原生自定义元素**渲染——DOM 里是 `<NDIVIDER>`（全大写、`display:inline`、**0 宽 0 高**、无 `.n-divider`），**不报任何错、不警告**，只是那根分割线凭空消失、上下间距全没了。排查法：`getComputedStyle(el)` 看 `display`，或看 DOM 标签是否仍是大写自定义名（正常应是小写 `<div class="n-divider">`）。**加了新 naive 组件后，第一件事是回头补 import**。
45. **`iframe srcdoc` 做可编辑预览时，绝不能把 srcdoc 做成响应式绑定**：LayoutPanel 右栏要让用户直接改 HTML（`contenteditable`），如果写成 `:srcdoc="html"` 这种**响应式**绑定，用户在 iframe 里每敲一个字 → 触发 `input` → 回写 `editedHtml` → 触发重渲染 → iframe 整个重载 → **光标跳回开头**，根本没法连续打字。正确做法是「**initialDoc 只设一次**」：用一个**非**响应式的一次性变量（`initialDoc`）只在 `rebuildPreview()` 里赋值，模板写 `:srcdoc="initialDoc"`（值本身不随输入变化，不会触发重载）；然后在 `@load` 回调里给 `doc.body` 挂 `oninput`，做**防抖 300ms 单向回写** `editedHtml = doc.body.innerHTML`，编辑期**禁止**再从 Vue 侧回灌 srcdoc。左栏（Markdown 编辑）与右栏（HTML 编辑）之间也不做双向同步，避免互相打架。
46. **新建表必须在 `models/__init__.py` 里 import，否则 `create_all` 建不出来**：项目没有 Alembic，建表靠 `Base.metadata.create_all`。而 `create_all` 只扫描**已经被 import 过的** `Base` 子类——如果你在 `models/settings.py` 里新写了 `class AppSetting(Base)`，但没在 `models/__init__.py` 里 `from app.models.settings import AppSetting`，那么 `init_db()` 时 `AppSetting.__table__` 根本没进 metadata，**建表被静默跳过**，运行时报 `no such table: app_settings`。**加新表的三步缺一不可**：① 模型文件写好；② `models/__init__.py` 导入并加进 `__all__`；③ 重启后端触发 `init_db()`。已存在的表要**加列**则另走 `_SQLITE_COLUMN_PATCHES`（见坑 29），`create_all` 不会替老表加列。
47. **确认端点 `POST /api/chat/confirm` 的 `conversation_id` 是「可选」，别塞占位串**：队列页与加工面板的「推送草稿」**不来自任何对话**，早期前端图省事把它们硬编码成 `conversation_id: 'queue'`，结果后端拿 `'queue'` 去 `conversations` 表查 → 查不到 → `raise HTTPException(404, "会话不存在")`。现象很迷惑：**接口本身是好的（不是路由 404），是路由内的业务 404**，表现为「接口 404 + detail: 会话不存在」。正确姿势：这两个入口**根本不要传 `conversation_id`**（schema 已是 `str | None = None`），后端**传了才校验**、查不到才 404、**有会话才** `add_message` 回写；省略/`null`/`""` 一律跳过校验与回写。下游 usage 统计、`Content.conversation_id` 都用 `.get()` 取值且列可空，无会话落 `NULL` 属预期。**排查同类「接口 404」时先看 detail 文案**：`{"detail":"Not Found"}` 才是路由不存在，带业务中文 detail 的是应用层自己抛的。
48. **占位符替换必须用「显式白名单」，别宽匹配 `{{…}}`**：组件库有 40+ 种槽位（`{{顶部标签}}`/`{{简介段落}}`/`{{LOGO占位}}`…），模型可能把没填的槽位原样留在 HTML 里。`services/author.py` 用 `_KEYS = ("作者名","一句话简介","号名","slogan")` 白名单 + 每键一条正则（`\{\{\s*键名\s*(?:[，,][^{}]*)?\}\}`，可吃掉 `，说明` 后缀），**只有白名单内的键会被替换**。加新键时只改 `_KEYS` + 传入 mapping，别写第二条 `re.sub`——两处并行的替换逻辑迟早分叉。**注意 `{{简介}}` 与 `{{一句话简介}}` 疑似别名、`{{LOGO占位}}` 是 olive-journal 的 logo 墙，都不要纳入**。
49. **「只在文末放关注卡」用标记注释剥离，别用嵌套 `<section>` 正则删除**：开头关注卡是**多层嵌套 `<section>`**，纯正则 `r"<section.*?</section>"` 非贪婪会错配（第一个 `</section>` 只是内层闭合）。做法：组件库用 `<!--OPENING_FOLLOW_CARD-->…<!--/OPENING_FOLLOW_CARD-->` 精确包裹，后端整块删；模型丢了标记时，用「配对栈」扫 `<section` / `</section>` 求出**包含目标文案的最内层完整 section 区间**再删。二维码槽同理用 `<!--QRCODE_SLOT-->` 标记包裹，未配二维码时整块删（不留空白行）。
50. **账号级资源（如公众号二维码）不要塞进 `Content.images`**：内容图片会被 `_image_manifest` 列进排版提示词、被 `<!--IMG:n-->` 索引、被封面逻辑当候选——账号级、跨文章复用的资源（二维码）混进去会**污染内容图片体系**。正确做法：独立目录 `data/uploads/qrcodes/{account_id}/` + 独立上传/静态服务端点。**另外**：这类图不在 `content.images` 里，`transfer_inline_images` 不会转存到微信，**推送前必须单独转存**（`push_wechat_draft` 里用 `_resolve_wechat_account` 取账号 → `upload_image`），否则发布后外链失效。
51. **沙箱出网 IP 是动态池，微信白名单建不完 → 用「仅微信请求走固定出口代理」**：实测一次采样（跨 ifconfig.me / icanhazip / ipinfo / ipify 多源）就探到 **20+ 个出口 IP**，且会漂移。而微信「API IP 白名单」**只收单个 IP、不收 CIDR**，逐个加白追不上。解法：让**仅微信请求**经一台固定公网 IP 的机器出网——`deploy/proxy-guard.sh` 在本地建 `ssh -D` 的 SOCKS5（出口即那台固定机器），后端 `.env` 设 `WECHAT_PROXY=socks5://127.0.0.1:10800`。要点：① 只改 `services/wechat.py`，**不设全局 `HTTPS_PROXY`**（免得 LLM/生图也绕道）；② 需要 `httpx[socks]`（即 `socksio`，装在后端那个 pyenv 里，不是系统 python3）；③ SSH 隧道长连接会**偶发瞬断**（`httpx.RemoteProtocolError: Server disconnected`），multipart 上传尤其明显——微信客户端对 `httpx.TransportError` 自动重试 1 次，且上传前把文件读进内存（重试要能重放 body）；④ 探测多源需重试，单源（如 ifconfig.me）抖动会误判「出口无」。守护脚本每 15s 校验实际出口 IP，不符即重建隧道。`WECHAT_PROXY_EXPECT_IP` 填进白名单即可（1 个 IP 搞定）。
52. **用 DB 标记（`Content.processing`）给长任务做互斥时，必须有「三条解除路径」**：`processing` 在任务开始置 `layout`/`image`、在 `finally` 清空。但它**只在任务真正收尾时才清**——一旦**进程重启/沙箱休眠/前端中途关面板**，正在跑的协程没了、标记却留在库里，队列页该行所有操作按钮（`disabled: busy`）被**永久禁用**（用户实测踩过：「排版中的任务退出后无法点击」）。所以三条路径缺一不可：① worker 的 `finally`（正常路径）；② **服务启动时** `recover_stuck_processing()` 统一清空残留标记（`main.py` 的 lifespan 里调，重启即自愈）；③ **前端手动「取消」**→ `POST /content/items/{id}/cancel-processing`（面板关闭时也自动调）。**连带坑**：队列页轮询不能只看「有没有 processing 就一直全量 refresh」——标记残留会变成**永久轮询**；要改成「只定向刷新当前页的处理中行」且组件卸载/无加工任务立即停。**再连带**：队列列表必须分页（`page`/`page_size` + 返回 `total`），否则数据增长后全量拉取+渲染会卡；分页后**筛选要在后端做**，前端不能再 `filter()`，否则每页条数对不上。
53. **窄屏别只靠 CSS `display:none` 隐藏核心功能区，必须给等价入口**：对话创作页的会话列表原本只在桌面侧栏（`.conv-panel`）里，窄屏媒体查询直接 `display: none` 把它藏了 —— 结果是**手机上完全看不到、也切不了已有会话**（用户实测：「移动端对话创作模块，无法显示已有会话」）。修复不是「把侧栏硬塞进一列」（240px 侧栏挤在 390px 屏上没法用），而是**换交互形态**：桌面用常驻侧栏，窄屏用**左侧抽屉**（`NDrawer` + 工具栏「☰ 会话」按钮）。三个要点：① 列表本体抽成**共用子组件** `ConvList.vue`（props/emits 只管展示与事件，重命名/删除动作由父组件执行），桌面侧栏与移动抽屉复用同一份，行为才不会分叉；② 断点用 `isMobile`（`window.innerWidth < 768`）+ `resize` 监听，模板 `v-if` 切换（不是纯 CSS），这样抽屉里的 DOM 在桌面根本不存在；③ **触屏没有 `hover`** —— `.conv-actions`（重命名/删除按钮）原本靠 `:hover` 露出，手机上永远出不来，要补 `@media (hover: none) { .conv-actions { display: flex } }` 兜底。**排查同类「某功能在手机上不见了」时，先全局搜 `@media (max-width: …)` 里的 `display: none`**，看被藏的是不是核心功能而不只是装饰。
54. **「只读」由队列状态驱动，别把 status 灌进 `ContentItem`**：已发布（`QueueItem.status === 'published'`）的任务不该还能改，面板要转成只读「排版详情」。关键设计：**只读与否是「队列项」的属性，不是「内容」的属性** —— `ContentItem` 天生不含队列状态（同一份内容可能挂在多个队列项上，各自发布进度不同），把 status 塞进内容模型会污染它。所以 `LayoutPanel` 的 `readonly` 由调用方 `QueueView` 按 `row.status === 'published'` 传入。落地要点：① 只读时要收的不只是按钮 —— 作者行、主题选择、左栏 MarkdownEditor（换 `MarkdownView` 只读渲染）、右栏预览 iframe 的 `contenteditable`（`rebuildPreview()` 里按 `isReadonly` 取 `'false'`/`'true'`，且只读时**不挂** `oninput` 回写监听）、下方 `ImageManager`（给它加 `readonly` prop，隐藏生成/上传/设为封面/删除，只留预览）**都要一起收**，漏一个就还能改；② **保留只读动作**：复制富文本、预览宽度切换、全屏；③ 面板打开有两条路径 —— 列表点「查看排版」（拿得到 `row.status`）与推送时「还没排版，去加工」的兜底路径（`openLayoutFromContent`，恒为可编辑），**后者必须显式置 `false`**，否则会误判成只读；④ 标题统一为「排版详情」（不再叫「加工排版」），并加「已发布 · 只读」标识让人一眼看懂为什么不能改。
55. **naive-ui 2.45 没有 `NTour`，做引导要自研（或换库）**：想加「新手引导/聚光灯导览」时第一反应是找组件库的 `Tour`，但项目实际装的 **naive-ui 2.45.3 `es/` 目录下根本没有 `tour`**（只有静态的 `steps`，那是步骤条不是浮层导览），直接 `import { NTour } from 'naive-ui'` 会拿到 `undefined`。**先 `ls node_modules/naive-ui/es/ | grep -i tour` 确认再动手**，确认没有就走自研（`components/GuideTour.vue`）。自研聚光灯最省事的写法是「透明框 + `box-shadow: 0 0 0 9999px rgba(0,0,0,.55)`」挖洞，别去算四块遮罩。**跨页引导必踩的两个坑**：① 路由是 `createWebHistory`（路径是 `/queue` 不是 `/#/queue`），写 `#/` 会静默留在原页；② 页面组件是**懒加载**的，`router.push` 返回后立刻 `querySelector` 往往拿不到目标元素 —— 必须**轮询等锚点出现**（本项目 60ms 一次、最多 1.6s），拿到后再 `scrollIntoView` + 等一帧取 `rect`。③ 窄屏气泡贴底，若高亮目标也是贴底元素（移动端底部导航），气泡会盖住目标 → 目标落在下半屏时把气泡改贴顶。
56. **「只弹一次」的引导：看完和跳过都要写标记**：引导的存储键（本项目 `localStorage.cwb_onboarding_done`）在**两条**退出路径上都要写 —— 走完（`finish`）与主动跳过（`skip`/`Esc`）。只在 `finish` 里写会让「跳过」变成每次刷新都再弹一次，比不做引导还烦。读写在 `stores/onboarding.ts`，沿用 `stores/theme.ts` 的 try/catch 范式（隐私模式下 `localStorage` 会抛异常，读失败按「没看过」处理，最多多弹一次不影响使用）。手动重看 = `reset()` 清标记 + 打开，且 **`reset` 不能让自动弹逻辑复活**（`App.vue` 的自动弹只在 `onMounted` 判一次）。
57. **要让底部固定元素（输入框/工具条）钉在容器底、中间内容自己滚动，flex 高度链有三处必踩**：典型症状是「消息一多，输入框被顶出视口，必须下拉才看得到」。逐层排查：
    - **① 组件库会把内容再包一层，断掉 flex 链**。naive-ui 的 `NCard` 根元素是 `display:flex; flex-direction:column`，但它把内容塞进 `.n-card-content`（**注意类名是 `n-card-content`，不是 `n-card__content`**），而这层是 `display:block` —— 里面写的 `.msg-scroll{flex:1}` 在 block 父级里**毫无意义**，消息区按自然高度撑开。修法：`.chat-card :deep(.n-card-content){ display:flex; flex-direction:column; min-height:0; flex:1; }`。**别顺手把 `padding-bottom` 删掉**：`--n-padding-bottom`（默认 12px）正是输入框和卡片底边之间那点呼吸空间，删了输入框会紧贴卡片底、很难看（实测踩过：先删了贴底，用户反馈「紧挨着底部了，应该有一定空间」，又加回来）。
    - **② 子组件根元素不带 scoped 的 `data-v-*`，普通作用域选择器静默失效**。`NScrollbar` 渲染出的根元素**只有 class/role/style 三个属性**（实测），所以 `.msg-scroll[data-v-xxx]` **永远匹配不上**，`flex:1` 形同虚设。必须写 `:deep()`（生成 `[data-v-xxx] .msg-scroll`，靠祖先匹配）。**排查手法**：遍历 `document.styleSheets` 找出真正命中该类的规则，或直接 `el.getAttribute('data-v-xxx') === null` 判定。对比：`NCard` 的根元素（`.chat-card`）**确实带** `data-v-*`，所以 `.chat-card :deep(...)` 能正常工作。
    - **③ Grid 行高默认 `auto`（= 内容高度），会被内容顶高**。`grid-template-columns:240px 1fr` 只声明了列，行高就是 `auto`，消息一多整行跟着变长、整页变长。修法加 `grid-template-rows: minmax(0,1fr)` 把行高锁成容器高度。同理，高度链的每一环都用 **`flex:1 + min-height:0`**，别用 `height:100%` —— `height:100%` 需要父级有*确定*高度，链路中有一环是 `auto` 就退化成按内容撑高（本项目实测 `.chat-card` 拿到 `flex:0 1 auto; height:2772px`，就是被内容撑的）。
    **验证手写**：CDP 注入 60 条假消息压测，断言 ①输入框与卡片底边之间**留 4~28px 呼吸空间**（不是紧贴！本项目实测落在 13px = 卡片 12px `padding-bottom` + 1px 边框）；②输入框 `bottom <= 视口高`（不再需要下拉）；③卡片高度空态与长会话**一致**（未被撑高）；④消息容器 `scrollHeight > clientHeight`（内滚而非撑高）。
    > **判定标准要写对**：「贴底」的正解是「**钉住 + 留白**」，不是「紧贴到 0px」。用户第一轮说「要和底部齐平，不然要下拉」，第二轮紧接着说「又紧挨着了，应该有空间」—— 两头都要满足：元素必须在视口内，但不能死贴着容器边。
58. **「思维链/工具痕迹落库 + 历史回显 + 反跳定位」有一整组连环坑**（2026-10 对话增强，实测全踩过）：
    - **① assistant 行「先建后重置」，否则流尾重复插一条**。`tool_confirm` 落地时要先把累积的 `tool_trace` + pending 写成一条 assistant 消息，落库后**必须立刻重置三个累积器**（`collected_text`/`collected_reasoning`/`tool_trace`）——不重置的话流结束后「有内容就落行」的逻辑会把同一段回复**再插一遍**。流尾的落行条件也要从「无条件落」改成「`collected_text or collected_reasoning or tool_trace` 才落」，否则「只有工具调用、没有正文」的回复会被整条漏掉。
    - **② 反跳定位靠「客户端 id 当 DB 主键」**。前端为回复预生成 `assistant_msg_id`，落库时直接当主键（`add_message(msg_id=...)`），于是「保存到队列」上报的 `msg_id` 与历史消息 id **天然一致**，队列页反跳 `/chat?conversation_id=…&msg_id=…` 才能零猜测定位。两边的 id 各生成各的，就永远对不上。
    - **③ 展示结构与模型结构是两套，边界在 service 层**。库里存**展示型** `{"calls":[{id,name,arguments,result,status}]}`（给人看）；`build_context` 发给模型前必须转成 OpenAI 格式：`assistant(tool_calls=[…])` + 逐条 `tool(tool_call_id, content=result)` 消息，`status=pending` 的用占位 result。**`reasoning` 一律不回灌**（省 token，且不认 reasoning 的 provider 会直接报错）。
    - **④ SQLAlchemy 的 JSON 列原地改嵌套 dict 不标记 dirty**。`msg.tool_calls["calls"][0]["result"] = r` 之后 `commit()` **不落库**（静默丢失）。必须浅拷贝出 list、改完**整体重新赋值** `msg.tool_calls = {"calls": calls}` 才会触发 UPDATE。
    - **⑤ 滚动联动高亮只认「目标 role」的消息**。取「容器内最后一个滚过顶部的消息」当 active 时，选择器写成 `.msg[data-msg-id]` 会把 assistant 也算进去——没滚动的场景下 current 落在最后一条 assistant 上，而它的 id 根本不在导航目录里，**active 永远高亮不了**。必须收窄成 `.msg-user[data-msg-id]`。另外 active 不能只靠 `scroll` 事件驱动：流式追加、切换会话都会改变 DOM 但不产生滚动，要 `watch(() => messages.length)` + `watch(() => activeId)` 主动跟算。
    - **⑥ CDP 验证脚本里，IIFE 少一个括号会被静默求值成函数**。对象字面量 IIFE 的正确尾巴是 `}))()`；写成 `})()`（语句体的尾巴）时 `Runtime.evaluate` 不报错，返回 `{type:"function"}`，下游以 `KeyError` 的形式莫名失败。**给 `ev()` 加一句防御：`result.type === "function"` 直接抛**，别让这类静默错误拖慢排查。
    - **⑦ 折叠态的默认值分场景**：流式中默认展开（思考流出是新用户最想看的东西），**历史回显默认折叠**（先看正文）。实现不是「一个全局默认值」，而是 `openConversation` 后对带 reasoning 的历史消息预置 `collapsed[id]=true`，不动用户手动切过的项。
59. **「不占空间的 hover 浮层」怎么做（DeepSeek 式提问导航，2026-10 重构）**：常驻竖栏 216px 太占空间，改成「默认一列小横线 marker，hover 才弹概要」。要点：
    - **① 视觉与热区分离**。marker 的点击热区是 18×12 的 `<button>`，视觉只是里面一根 10×2 的小横线（子 `<span>`）——直接拿 2px 高的条当点击目标根本点不中。active 态（当前阅读位）用主色 + 更长更粗区分。
    - **② 浮层必须 fixed 定位，坐标用 JS 按 marker 的 rect 算**。`position: absolute` 会被窄轨祖先（20px 宽）裁掉；fixed + `getBoundingClientRect()` 算 left/top，垂直中心对齐 hover 的 marker，再用 `Math.max/min` **钳制在视口内**（贴顶/贴底时整体平移，绝不伸出屏幕）。轨是 grid 第三列，注意 grid 列宽变化（216px → 20px）会连带改变主区宽度。
    - **③ 鼠标从 marker 移进浮层有 8px 缝隙，`mouseleave` 直接收起会永远进不去**。标准解法：**延迟隐藏**（本项目 160ms）+ 浮层自己的 `mouseenter` 取消定时器；点击 marker 或浮层项后立即收。
    - **④ 浮层里的滚动列表用原生 `overflow-y:auto`，别用 NScrollbar**。NScrollbar 根元素不带 scoped 的 `data-v-*`，在 scoped 样式里写 `max-height` 会**静默失效**（坑 57②），浮层限高直接崩；原生 overflow 配 `scrollbar-width: thin` + `::-webkit-scrollbar` 就有参考图里那种细滚动条。
    - **⑤ 两种高亮语义分开**：轨上的 active 条 = 「当前阅读位」（跟随消息区滚动联动，只认 user 消息，坑 58⑤）；浮层内的高亮 = `hoveredId || activeId`（鼠标悬停谁就临时置顶高亮谁）。混为一个会导致「鼠标一划过，阅读位乱跳」。
    - **⑥ 窄屏没有 hover，形态必须换而不能藏**：收成卡片顶部横向 chips（`mode` prop 切形态），**两种形态复用同一份数据与同一个 `jump` 事件**——交互逻辑分叉是这类改写的最大风险。
    - **⑦ 验证要覆盖「默认态不占空间」本身**：断言轨宽 ≤24px、默认无浮层 DOM、hover 后浮层完整在视口内、离开后收起、点击两种入口都能定位。布局回归别忘：主区宽度、输入框贴底（坑 57）都会因列宽变化受影响。

60. **用户模块（JWT + bcrypt + 直链 HMAC）的一整组要点**（2026-10 上线，替代 `X-Owner-Id` 自称机制）：
    - **① 用户 id 直接当 owner，靠薄封装让 53 处签名不动**。`current_user` 返回 User 对象，`current_owner_id` 是返回 `user.id` 的薄封装——`Depends(current_owner)` → `Depends(current_owner_id)` 机械改名，端点函数体零改动。别反过来把 User 对象塞进签名，那样 53 个函数体全要加 `.id`， diff 大十倍。
    - **② JWT secret 必须持久化**。`JWT_SECRET` 留空时首次启动生成并写 `data/secret.key`（0600）。拍默认常量 = 签名密钥进 git 历史；每次随机 = 重启后全部 token 失效。直链 HMAC 与 JWT 共用这一个 secret。
    - **③ bcrypt 直接用库，别引 passlib**。passlib 1.7.4 与 bcrypt 5.x 有兼容问题（读不到 bcrypt 版本信息），为一个哈希函数背这个风险不值。
    - **④ 首用户认领必须同事务**。注册 + `UPDATE owner='default'→uid` + 旧 URL 重签 + voices 目录搬家在同一个事务里。URL 重写要**逐条来**（sig 按 path 算，不能 SQL 批量 replace）；JSON 列先 dumps 成字符串做正则替换、解析失败就跳过，不阻塞认领；voices 搬迁靠 `profiles_dir()` 早有 `owners/<owner>` 分支，纯 `shutil.move`。
    - **⑤ 登录页要渲染在 App 外壳之外**。未登录时 `queue.refresh` 等后台轮询只会 401——`App.vue` 用 `v-if="auth.isAuthenticated"` 把整个工作台壳（含 GuideTour）换掉。401 拦截器要**防环**：登录/注册页自身的 401 不跳转（靠 `location.pathname` 判断）。`main.ts` 先 `await auth.bootstrap()` 再 `app.mount`，否则刷新会先闪一下工作台再被守卫踢去登录页。
    - **⑥ 测试别用 TestClient 的 `with` 块**。lifespan 里的 `init_db()` / `recover_orphans()` 会经**全局 engine** 碰开发库，且 TestClient 的 portal loop 与 pytest 主 loop 不是同一个，全局 engine 的连接池跨 loop 直接报错。正确姿势：`TestClient(app)` 不进 with（不触发 lifespan）+ `dependency_overrides[get_db]` 换测试库（文件库 + `NullPool`）+ monkeypatch 直接 import 的 `settings` 单例。另外 `services/render.py` 的 `get_job()` 内部直连 `SessionLocal`（不经依赖注入），测它得 monkeypatch `app.services.render.SessionLocal`。
    - **⑦ slides 撞目录用 claim 表修**。幻灯片目录名是 `md5(pptx)[:16]`，两人上传同一份 PPT 会撞——`PptSlideClaim` 懒认领（无记录登记为当前用户，有记录且归属不符 404），配合 `link_auth` 双保险。懒认领的写入要在 `path.is_file()` 确认之后，别给不存在的目录建 claim。

61. **App.vue 里别用 `v-if` 分叉出两个 RouterView，认证页要做成顶层路由**（2026-10 实测踩过）：想在未登录时只渲染登录/注册页，直觉写法是 `<div v-if="!isAuthenticated"><RouterView/></div>` + `<NLayout v-else>…<RouterView/>`。**这会让登录态一变，当前路由组件被销毁重建**——注册成功后 `user` 一赋值，未登录分支的 RouterView 卸载、RegisterView 销毁，组件里刚赋值的「存量接管摘要」`ref` 归零，页面退回空表单（用户名还被占用了，排查半天以为后端没认领）。正确结构：**认证页（/login、/register）做成顶层路由，工作台全部挂在 `layouts/AppShell.vue` 的 `children` 下，App.vue 只留 Provider + 唯一一个 `<RouterView/>`**。判断「外壳要不要渲染」的职责交给路由层级，而不是 v-if。
    - **连带坑：调子组件查不到问题时，先确认组件没被重建**。现象是「赋值成功但 UI 不动」，`console.log` 能打印新值、模板就是不更新——如果是父级 `v-if` 切换导致的重建，值其实赋上了，只是赋给了一个马上被销毁的实例。验证法：`onUnmounted` 里打日志，看赋值后组件是不是死了。
    - **连带的坑 56 修正**：新手引导会在登录后自动弹出（全屏遮罩 + 跨页跳转），自动化验证认证链路时要先 `localStorage.setItem('cwb_onboarding_done','1')` 预置「已看过」，否则引导的遮罩会挡住退出按钮、引导的跳转会劫持 URL，让验证脚本误报。

62. **反向代理的 `auth_basic` 和应用内 Bearer 认证是互斥的，不能叠加**（2026-10 公网部署实测）：想在应用之外「再加一层」nginx 密码保护，结果是**能打开登录页、能登录，登录进去之后所有接口全 401**。原因：两套认证抢同一个 `Authorization` 头。前端登录后每个 XHR 带 `Authorization: Bearer <jwt>`，而 nginx 的 basic auth 期望 `Authorization: Basic <base64>`——它看到 Bearer 就当没带凭证，直接回 401。**两层认证不是叠加关系，是互斥关系**，有应用内认证就必须摘掉代理层的 basic auth（见 `docs/Cloudflare-Tunnel接入说明.md` 5.5）。
    - **摘掉之后防暴力破解要靠应用层，且不能改用 nginx `limit_req` 按 IP 限**。Cloudflare Tunnel / SSH 反向隧道这类架构里，cloudflared 是**从本机回源**的，`$remote_addr` 恒为 `127.0.0.1`（`docs/Cloudflare-Tunnel接入说明.md` 5.3 有实测），按 IP 限流会把所有访客算成同一个 IP，正常用户被误伤、攻击者一个人吃掉全部配额。要限就在应用层取 `X-Forwarded-For` 里第一个**非内网**地址（nginx 的 `$proxy_add_x_forwarded_for` 会把它追加进来）。
    - **限流只按用户名是不够的**。本项目登录限流是「用户名 5 次 + 客户端 IP 20 次 / 15 分钟」双维度——只按用户名时，攻击者每试一个新名字就拿一份新配额，等于没限。XFF 虽然可伪造，但伪造了仍受用户名那档约束，两层足够。登录成功只清用户名那一档，IP 那档要留着，否则「撞库成功一次」就能把配额洗白。

63. **RBAC 的四个「看起来都对、实际上都会出事」的写法**（2026-10 上线实测推演）：
    - **`role` / `is_active` 别进 JWT**。令牌 7 天有效，把角色签进去意味着改一次角色要等 7 天生效（或强制所有人重登）。每次请求多一次主键查询，换来「停用即时生效」——被踢出团队的人手里的旧 token 下一次请求就 401，这才是停用的意义。
    - **管理员账号要系统预置，别搞「第一个注册的人自动 admin」**。那是把权限交给时间顺序：谁先打开页面谁拿管理员，路人甲也一样。正确做法是启动时 `ensure_admin_account()` 保证 `ADMIN_USERNAME` 存在且是 admin——已存在只摆正角色、**绝不动密码**（覆盖用户自己设的密码等于把人锁在自家系统门外）；不存在才创建，初始密码随机生成打进日志（只打创建那一次）。
    - **查「有没有 admin」时别带 `is_active` 过滤**。停用 ≠ 撤权。如果按「活跃 admin」判断，把所有 admin 停一次再重启，系统会认为「没有管理员了」于是另立一个——停用人反而成了获得管理员的手段。
    - **`link_auth` 的 HMAC 分支别跟着封停用用户**。历史配图 URL 签名绑 `?o=<uid>` 且已写进正文 HTML，停用就封会让存量文章配图集体 404——那是牵连读者，不是惩罚被停用的人。只封 Bearer 那一档。
    - **附带两个小坑**：① 管理统计别复用 `usage_svc.summary(db, owner=...)`，它内部 `owner or "default"` 兜底，传 None 会去统计 `default` 租户而不是全站；② 聊天消息早有一个 `role: 'user'|'assistant'|...`（`types/index.ts`），RBAC 的类型要另起名（`Role`，只放 `api/auth.ts`），别混。

64. **邀请码扣减要原子、`max_uses` 要 fail-open、用过的码不能删**（2026-10 上线）：
    - **扣减走单语句条件 UPDATE，别「读出来 +1 再写回」**。后者并发下会超发：两个请求同时读到 `used=2, max=3`，都以为还能用一个，实际用了 4 次。`core/invite.py` 的 `consume()` 用 `WHERE disabled=0 AND (max_uses IS NULL OR used < max_uses)`，`rowcount==0` 就是「不存在/已停用/已用尽」，统一抛「邀请码无效或已用尽」（模糊文案，别泄露码是否存在）。
    - **`max_uses` 缺失 / 0 / 负数 = 不限，绝不等于 0 次**。fail-closed 会让新码一生成就是废码。管理页输入框留空、传 0、传负，后端都归一成 `NULL`。
    - **用尽 ≠ 停用，且用过的码不能删**。用尽是 `used >= max_uses` 的即时判断（不改 `disabled`），渠道历史要保留；删除只允许 `used=0` 的码——用过的码是用户「来源」的依据，删了渠道归因就断。要作废就用停用。
    - **撞码要计入 IP 限流**。邀请码比密码熵低（且没有用户名维度兜底），只能靠 IP 挡遍历。注册改造时别把 `_record_fail(ip_key)` 弄丢——`consume()` 抛 403 时要补记失败（`tests/test_auth.py::test_register_rate_limit_on_bad_invite_code` 专门盯着这条）。
    - **迁移要幂等**：`import_legacy_code()` 启动时把 .env 旧码导入为不限次记录，已存在就跳过，重复启动不报错不重复建。

65. **细粒度权限/配额的几个「语义陷阱」**（2026-10 上线）：
    - **权限点不进 JWT**，每次请求现算（`/auth/me` 返回快照）。7 天有效期的令牌签进权限点，改完要等 7 天生效；现算换来「管理员改完、被改的人 60 秒内生效」。
    - **菜单级权限默认全开（fail-open）**。反过来（默认不含 menu.*）会让「取消勾选」变成「新成员侧栏直接是空的」。
    - **admin 权限不可收窄但配额照走**。管理页给 admin 配的额度必须真的生效，否则 UI 在说谎（配额是成本闸门不是权限）。
    - **覆盖是增量不是快照**。快照会把用户钉死在「管理员改他那一刻」的角色状态，模板升级传不下去。
    - **SSE 端点的配额必须在依赖里拦**，别写在函数体里——SSE 一旦返回 200 就改不了状态码了。
    - **测试要 patch 所有持有模块级 `SessionLocal` 的模块**（rbac / quota / chat / invite），漏一个就绕过测试库去碰开发库。
