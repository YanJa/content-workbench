# 素材库模块调研与实现方案

> 目标：建一个素材库，能按关键词采集图片/视频、处理水印、本地或云存储，并在写文章时直接取用。
> 本文先给结论，再给依据。**第 3 节的图源条款、第 5 节的水印合规**是动手前必须先看完的两段——
> 它们直接否掉了两个想当然的设计。

---

## 1. 一句话结论

**技术上不复杂，卡点在「素材从哪来」和「水印能不能去」。**

现有工程已经具备七成地基：`UPLOAD_DIR` 本地存储、`Content.images` 的 JSON 配图结构、
HMAC 签名图片路由、`loop_hot_fetch` 后台定时抓取范式、`create_all` 自动建表。
真正需要新写的只有三块：**Asset 数据模型 + 存储抽象层 + 采集适配器**。

三个结论先说：

1. **能合法「存下来」的免费图源只有 Pixabay / Openverse / Coverr 三家。** Unsplash API 强制热链、
   不允许转存；Pexels 的新 API Key 已停止发放。这个约束是硬性的，不是偏好问题。
2. **「定期搜索囤图」不宜做成主力形态。** Pixabay 条款明确禁止系统性批量下载。建议主链路改为
   **「写文章时按选题关键词搜图」**，定时任务只做小批量预取（每任务每日 20 张以内）。
3. **去水印必须做合规闸门。** 水印分三类，其中「权属水印」（© / Copyright / 版权方 logo）
   删除属《著作权法》第 51 条明令禁止的行为，可行政处罚乃至追究刑责。
   素材库只能对「来源水印」和「自有素材」开放这个能力，且必须保留原图。

## 2. 需求拆解

| # | 能力 | 现状 | 缺口 |
|---|---|---|---|
| 1 | 采集（按关键词搜图/视频） | 无 | 图源适配器 |
| 2 | 去水印 | 无 | 图像修复管线 + 合规闸门 |
| 3 | 存储（本地 / 云） | 本地 `UPLOAD_DIR` + 签名 URL | 存储抽象层（当前路径硬编码在 `layout.py`/`auth.py` 等处） |
| 4 | 管理与检索 | 无 | Asset 表 + 素材库页 |
| 5 | 发布时取用 | `Content.images` + `upload_image` | 「从素材库选」入口（复用现有 images 结构，不改发布链路） |

第 5 点是关键判断：**不需要动发布链路**。`Content.images` 已经是
`{id, path, url, alt, source, prompt, position}` 的列表，素材库只要生成同形状的对象 append 进去即可。

## 3. 图源调研（本方案的核心约束）

### 3.1 条款对照

| 源 | 图片 | 视频 | 可否转存自建库 | 配额 | 署名 | 结论 |
|---|---|---|---|---|---|---|
| **Pixabay** | ✓ | ✓ | **✓ 条款要求必须自存**（禁止永久热链） | 100 req/60s，结果须缓存 24h，**禁止系统性批量下载** | 不强制 | **主力源** |
| **Openverse** | ✓ | ✗ | ✓（CC 系许可，可再分发） | 匿名 100/天、5/小时；带 key 10000/天、100/分钟 | BY/BY-SA 需署名 | **合规补充**，可按 `license_type=commercial` 过滤 |
| **Coverr** | ✗ | ✓ | ✓ | 免费 50 调用/小时 | 不要求 | **视频主力** |
| **Unsplash** | ✓ | ✗ | **✗ 强制热链**，必须用其 CDN URL | 50 req/小时（demo） | 必须署名 + UTM 回链 | **只做在线引用**，不入库 |
| **Pexels** | ✓ | ✓ | 条款允许 | 200/小时、20000/月 | 要求署名 | **暂不可用**（新 key 发放已暂停） |

> **Unsplash 这条最容易踩。** 其 API Guidelines 原文要求「所有 API 使用必须使用 `photo.urls`
> 返回的热链 URL」，包括用户选中图片插入文章之后的所有展示。若确需自建图床，得单独联系其 API 团队
> 谈 photo views beacon 方案。所以 Unsplash 只能做「搜到了、存 URL、用到时热链」，**不能下载入库**。

> **Pexels 的现实问题**：官方页面现在写着 "New API key issuance is currently paused and cannot be
> requested"。除非已有存量 key，否则这条路暂时走不通，不要写进 MVP。

### 3.2 选型建议

```
图片：Pixabay（主力，可自存） + Openverse（CC 合规补充，可过滤商用许可）
视频：Coverr（免费商用免署名） + Pixabay Videos（覆盖更广）
在线引用：Unsplash（只存 URL，不落盘）
```

三家都要**在界面上保留来源与署名**：Openverse 的 CC-BY 必须署名，Pixabay/Coverr 虽不强制，
但保留 `author` / `source_url` 元数据是零成本的合规保险，也是将来换源时的迁移依据。

### 3.3 「定期采集」的正确形态

条款里那句「系统性的批量下载不被允许」是硬约束。所以采集要分两种模式：

| 模式 | 触发 | 用量 | 合规性 |
|---|---|---|---|
| **选题驱动（主）** | 用户写某篇文章时，用标题/关键词搜一次 | 每次 1 请求，取 20 条 | 完全合规，属于「真人请求」 |
| **定时预取（辅）** | 用户预设「关键词 + 每天几点 + 最多 N 张」 | 每任务每日 ≤20 张，间隔 ≥1 小时 | 需限速 + 去重，避免重复下载同一批 |

**建议默认关掉定时预取，只保留选题驱动。** 理由有三：素材有时效性（囤的图半年后可能不合用）、
存储会无限膨胀、以及条款风险。真要预取，就当成「给常写领域备一点底图」的小工具，配额卡死。

## 4. 存储方案

### 4.1 现状盘点

- 图片落盘：`Path(settings.UPLOAD_DIR) / "gen" / <content_id> / <file>`
- 对外访问：不走 StaticFiles，走 `GET /content/images/{content_id}/{filename}`，
  用 `link_url()` 生成 HMAC 签名（`?o=<uid>&sig=...`），解决 `<img src>` 带不了 Authorization 头的问题
- 路径引用：DB 里存**相对 UPLOAD_DIR 的路径**（如 `gen/<cid>/xxx.png`）

这套设计很干净，素材库直接沿用，只是把「路径拼装」从各处收进一个存储抽象层。

### 4.2 抽象层设计

```python
# app/services/storage.py
class StorageBackend(Protocol):
    async def put(self, key: str, data: bytes, content_type: str) -> None: ...
    async def get(self, key: str) -> bytes: ...
    async def delete(self, key: str) -> None: ...
    async def exists(self, key: str) -> bool: ...
    def public_url(self, key: str, owner: str) -> str: ...
```

两个实现：

| 实现 | 说明 |
|---|---|
| `LocalBackend` | 写 `UPLOAD_DIR`，`public_url` 走签名路由（复用 `link_url`） |
| `S3Backend` | boto3 + `endpoint_url`，兼容阿里云 OSS / 腾讯 COS / Cloudflare R2 / MinIO；`public_url` 返回预签名 URL |

**关键决策：DB 里只存 `storage_key`，不存完整 URL。**

```
assets/<owner>/<yyyymm>/<asset_id>.<ext>
assets/<owner>/<yyyymm>/<asset_id>_thumb.webp
```

好处：换存储后端不用改一行数据（本地 ↔ 云直接切 `STORAGE_BACKEND` 配置）；
签名 URL 有有效期，本来就不该落库。现有的 `Content.images[].url` 是「算出来再存」的，
素材库不要沿用这个做法。

### 4.3 云存储选型

单机 sqlite 部署，云存储属于「可选增强」，不是必需。若要做：

- **Cloudflare R2**：无出网流量费，与项目已有的 CF 账号天然配套（省钱角度最优）
- **阿里云 OSS / 腾讯云 COS**：国内访问快，但走 CDN 有流量费
- **MinIO**：自建，适合彻底私有化

建议 **P0 只做 LocalBackend + 抽象接口**，`S3Backend` 留到有真实需求时再落，
避免为「可能用得上」付维护成本。接口留好，加 S3 只是新增一个类。

### 4.4 容量控制

现有 `app/core/quota.py` 是**按次计数**（`count` 列），不支持字节维度，不能直接复用。
素材库单独算：

```sql
SELECT COALESCE(SUM(bytes), 0) FROM assets WHERE owner = :owner
```

配上 `ASSET_QUOTA_MB`（默认 2048）配置项，超限拒收并在列表页显示占用条。
聚合查询量小，不需要额外建计数表。

## 5. 去水印：技术可行，但必须先划合规线

### 5.1 三类水印，法律待遇完全不同

依据北京斐普律师事务所与海淀律协的梳理（《去除作品上的水印侵权吗？》）：

| 类型 | 典型形态 | 去除的后果 |
|---|---|---|
| **来源水印** | 微博/小红书/B站自动加的账号名或平台 logo、电商店铺名、图库样本 ID | **通常不侵害著作权**（它只是来源提示，不等于署名）。但可能违反平台用户协议 |
| **署名水印** | 作者本名/笔名/艺名，明确表示「这是我拍的」 | **侵犯署名权**，需停止侵权、赔礼道歉 |
| **权属水印** | `© 2020 NBA Properties`、`VCG`、`Getty Images`、赛事版权标 | **属「权利管理信息」**，《著作权法》第 51 条明令禁止删除，除民事责任外可行政处罚、可追刑责 |

**所以「一键去水印」这个交互本身是有问题的**——它不区分处理对象。
素材库必须把它设计成「带前置校验的修复工具」，而不是一个万能橡皮擦。

### 5.2 产品层面的三道闸门

1. **声明来源**：上传/采集入库时必填 `license` 与 `source_url`。来自 Pixabay/Openverse/Coverr 的
   自动带；手动上传的必须勾选「我拥有该素材权利或已获授权」才能启用去水印按钮。
2. **权属水印拒处理**：对图片先做一轮文本检测——命中 `©`、`Copyright`、`All Rights Reserved`、
   `Getty`、`VCG`、`视觉中国` 等关键词，或检测到的水印区域位于「整幅图居中/通铺」这种版权标典型位置时，
   **直接拒绝并说明原因**，不给用户「我知道了，继续」的选项。
3. **保留原图 + 留痕**：`original_key` 永不覆盖，产物另存；`Asset` 上记
   `watermark_removed_at`。发布时若需追溯，链路完整。

这三道闸门不是法务免责声明，是产品逻辑的一部分——它决定了这个功能是「修自己的图」还是「批量洗图」。

### 5.3 技术实现分三级

| 级别 | 方案 | 效果 | 成本 |
|---|---|---|---|
| **L1 裁切** | 按用户框选/固定角标区域直接裁掉 | 无损、无痕迹，适合四角条状水印 | 纯 PIL，零新依赖 |
| **L2 内容修复** | `cv2.inpaint`（TELEA / NS 算法） | 纯色/渐变/纹理背景效果好；复杂背景有「涂抹感」 | 新增 `opencv-python-headless`（约 60 MB） |
| **L3 AI 修复** | LaMa（`simple-lama-inpainting`）或 IOPaint | 效果最好，复杂背景几乎无痕 | 需 torch ≈ 2 GB，与项目「不默认装重依赖」原则冲突 |

**建议 P2 只做 L1 + L2**，L3 像声音复刻那样写成注释依赖，需要时再装。
理由：素材库的正当用途是处理自有素材的角标/相机水印，L1 裁切就够用；
L2 兜住「水印压在画面上」的情况；L3 的边际收益主要在「洗别人的图」，恰好是我们要避免的场景。

### 5.4 视频水印

视频去水印复杂度高一个量级（逐帧修复或模糊跟踪），且 ffmpeg 的 `delogo` 滤镜只支持矩形模糊。
建议 **v1 视频不做去水印**，只做「入库 + 转码 + 使用」。这不是能力问题，是投入产出比问题。

## 6. 数据模型

新增 3 张表（`create_all` 自动建，只需在 `models/__init__.py` 导入）：

### 6.1 `assets`（素材主表）

```python
class Asset(Base):
    __tablename__ = "assets"
    id: str                    # uuid hex 12
    owner: str                 # 租户隔离，与 Content 同口径
    kind: str                  # image | video
    source: str                # upload | search | ai | cover
    source_name: str           # pixabay | openverse | coverr | unsplash | ""
    source_id: str             # 源站 ID，用于去重与回查
    source_url: str            # 原页面地址（署名回链用）
    license: str               # pixabay-content | cc0 | cc-by | cc-by-sa | own | unknown
    license_url: str
    author: str
    author_url: str
    attribution_text: str      # 现成的署名行，发布时可自动附上

    title: str
    tags: list                 # JSON
    width: int
    height: int
    duration: float            # 视频秒数，图片为 0
    bytes: int
    mime: str
    hash_sha256: str           # 内容去重（跨源同图也能识别）

    storage: str               # local | s3
    storage_key: str           # 相对 key，不含域名
    thumb_key: str
    original_key: str          # 去水印前的原图（永不覆盖）

    watermark_state: str       # none | removed | rejected
    created_at: int
    used_count: int            # 被引用次数
    last_used_at: int
```

索引：`(owner, kind)`、`(owner, hash_sha256)` 唯一、`(owner, created_at)`。

### 6.2 `asset_fetch_jobs`（采集任务）

```python
id, owner, name, source_name, keywords(JSON), kind,
interval_minutes, daily_limit, max_per_run,
enabled, last_run_at, next_run_at, last_error
```

### 6.3 `asset_usages`（引用关系）

```python
id, asset_id, content_id, owner, created_at
```

作用：反查「这张图在哪些文章里用过」，删除素材前能提示影响面。
`Content.images` 里仍存一份快照（发布链路不变），这张表只是索引。

## 7. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/assets` | 列表：`kind/source/tag/q/from/to/sort/page` |
| POST | `/assets/upload` | 上传入库（自动算 hash、生成缩略图） |
| POST | `/assets/search` | **在线搜，不落库**，返回候选 + 许可元数据 |
| POST | `/assets/import` | 把候选下载入库（带 `source_id` 去重） |
| GET | `/assets/{id}/file` | 签名 URL 取文件（复用 `link_url` 机制） |
| POST | `/assets/{id}/watermark` | 去水印（异步任务，返回 `job_id`） |
| PATCH | `/assets/{id}` | 改标题/标签 |
| DELETE | `/assets/{id}` | 删除（有引用时需 `force`） |
| GET | `/assets/stats` | 占用容量、按源/类型分布 |
| POST | `/content/items/{cid}/images/from-asset` | **发布链路入口**：`{asset_id}` → append 进 `Content.images` |
| CRUD | `/assets/jobs` | 采集任务管理 + `POST /assets/jobs/{id}/run` 立即跑 |

搜索与导入分开，是因为**搜索结果不该污染库**——用户可能只是看看，选中了才入库。
这也顺带满足了 Pixabay「结果须缓存 24h」的要求（内存缓存即可）。

## 8. 前端

新增 2 个视图 + 1 个弹窗：

- **`AssetsView.vue`**（`/assets`）：网格瀑布流，左侧筛选（类型/来源/标签），顶部搜索框与容量条。
  支持多选批量删除、批量下载。卡片上标来源徽标（Pixabay / CC0 / 自有），
  署名要求非空的（CC-BY）在卡片角上显示作者名。
- **`AssetPicker.vue`**：弹窗形态，供 `ImageManager.vue` 调用。
  在 `ImageManager` 的工具栏加一个「从素材库选」按钮，选中后走
  `images/from-asset`，刷新 `images` 列表即可——**不改发布链路**。
- **去水印弹层**：在原图上拖框选区域 → 预览（L1 裁切 / L2 修复二选一）→ 确认。
  权限点 `assets.watermark`，单独由 RBAC 控制（默认只给管理员，避免被当洗图工具）。

顺带：`AssetsView` 要能「按当前文章的标题/关键词一键搜图」，这是最高频的入口。

## 9. 定时任务

沿用 `app/services/zhihu.py:loop_hot_fetch` 的范式（挂 lifespan，循环体吞异常，启动补跑）：

```python
async def loop_asset_fetch() -> None:
    # 每 5 分钟扫一次 due 的任务，而不是每个任务一个 asyncio 协程
    # —— 任务数动态增减，集中调度比散养协程好管理，也不会在重启后留下孤儿协程
```

四条纪律（照抄热点抓取的）：吞异常、启动补跑、未配置待命、成败都落审计。

**限速**：单任务每次 ≤ `max_per_run`（默认 10），每日 ≤ `daily_limit`（默认 20）。
两个数字都写进配置，不要硬编码——条款要求「真人请求量级」，这个上限就是合规边界。

## 11. 风险清单

| 风险 | 等级 | 应对 |
|---|---|---|
| **版权连带责任** | 高 | 免费图库都**不提供 indemnification**（Pixabay/Pexels/Unsplash 均为 $0 覆盖，且要求用户反过来赔偿平台）。因为任何人也可能把他人作品上传到图库。要真正兜底只能买付费图库（Shutterstock 单图 25 万美元）。方案内置 `license` + `source_url` 元数据，至少做到「可追溯、可下架」 |
| **去水印被滥用** | 高 | 三道闸门 + 权属水印拒处理 + 独立权限点 + 保留原图。**不做批处理** |
| **采集合规** | 中 | 限速 + 禁止系统性批量下载 + 定时任务默认关闭 |
| **存储膨胀** | 中 | 容量配额 + 缩略图 + 视频默认不转码（只存原片，用时按需） |
| **Pexels/Unsplash 能力误判** | 中 | 文档与 UI 明确标注「仅在线引用」「暂不可用」，别写在可用源列表里 |
| **已有图片路径硬编码** | 低 | 素材库走新抽象层；`layout.py`/`auth.py` 里的旧路径**先不动**（避免大范围回归），只在新增代码里统一 |

## 12. 需要拍板的 4 个点
