## 2. Agent 编排（为什么不用 LangChain）

内容运营的核心动作是「理解意图 → 生成内容 → 存成品 → 进队列 → 发布」。这是**确定性工作流**，不是开放式自主任务。手写编排的价值：

- 每一步可控、可测、可打日志；
- 依赖少（少一层框架抽象 = 少一类升级炸裂）；
- 模型只在「生成」和「决定调工具」两处出场，token 花在刀刃上。

`services/agent.py` 的循环（`MAX_TOOL_ROUNDS = 5`）：

```
run_chat(messages, task):
  1. build_context()      → system prompt + 历史摘要 + 最近 N 轮
  2. 调 LLM（stream=True, tools=registry.openapi_schemas()）
  3. 流式转发 delta 给前端（SSE）
  4. 模型要调工具？
     ├─ requires_confirm=false → 直接执行，结果回传模型继续
     └─ requires_confirm=true  → yield tool_confirm，循环暂停
                                 前端展示确认卡片，用户点确认
                                 → /api/chat/confirm 执行 → 回传
  5. finish_reason=stop → 落库，yield done
```

> **职责边界（2026-10-16 起）**：对话只产出**纯内容**，**不主动入队**。
> `save_content` 已改为 `requires_confirm=True` 且只落草稿（不建 `QueueItem`），
> 入队的唯一入口是前端气泡上的「保存到队列」按钮 → `POST /api/content/items`。
> 之前模型会自作主张入队，用户根本不知道队列里怎么多了东西，已收敛掉。

上下文管理（`services/conversation.py`）：

- 滑动窗口保留最近 `CONTEXT_WINDOW_TURNS`（默认 10）轮原文；
- 超过 `CONTEXT_SUMMARY_THRESHOLD`（16）轮时，把窗口外内容用轻量模型压成摘要（`SUMMARY_PROMPT`），摘要存 `Conversation.summary`，随 system prompt 注入；
- token 统计逐条记录在 `Message.prompt_tokens / completion_tokens`。

## 3. 模型路由与成本

`services/llm.py` 按任务类型路由，避免「所有事都用旗舰模型」：

| TaskType | 模型 | temperature | 用途 |
|---|---|---|---|
| copywriting | deepseek-flash | 0.85 | 三平台文案创作 |
| reasoning | deepseek-v4-pro | 0.60 | 选题策划、长文结构 |
| lightweight | deepseek-flash | 0.30 | 会话摘要、合规检查 |
| vision | deepseek-flash | 0.70 | 配图理解（Flash 原生多模态） |

三个省钱开关：

1. **Prompt Cache**：system prompt 固定放 messages 最前，DeepSeek 缓存命中后输入价降至 1/50。代价是 `prompts/platforms.py` 的措辞不能随便改——改一次缓存全失效。
2. **峰谷感知**：`is_peak_hour()` 判断工作日高峰（北京时间 09:00–12:00、14:00–18:00），高峰调用打警告日志，批量任务引导到低谷跑。
3. **本地化媒体**：配音用 edge-tts（合成时直接拿 SentenceBoundary 当字幕轴），画面用 PIL 本地绘制、ffmpeg 本地合成，全部零 API 成本。

## 4. 工具系统

`tools/registry.py` 用装饰器注册：

```python
@tool(
    name="push_wechat_draft",
    description="把公众号文章推送到草稿箱",
    requires_confirm=True,      # 危险标记：前端出确认卡片
    timeout=30,
)
async def push_wechat_draft(title: str, html: str) -> dict:
    ...
```

5 个内置工具：

| 工具 | 确认 | 说明 |
|---|---|---|
| query_queue | 否 | 查发布队列状态 |
| check_compliance | 否 | 平台合规预检 |
| save_content | **是** | 存草稿（**不入队**），仅前端「保存到队列」显式触发 |
| push_wechat_draft | **是** | 推公众号草稿箱（凭证：指定号 → 默认号 → `.env` 回退） |
| render_video | **是** | 提交视频渲染 |

设计要点：

- `execute()` 带超时与异常隔离，工具崩了只返回 error 字段，不炸主流程；
- 凭证缺失（如没配微信 AppID）时优雅降级，返回可读的错误说明而非 500；
- 加新工具 = 写一个函数 + 挂装饰器，openapi schema 自动生成给模型。

## 4.1 排版引擎（方案 A'：组件库当提示词资产 + LLM 装配）

**为什么对话和排版要分两层**：对话侧要的是「好改」——用户提意见，AI 直接产出完整新版本 Markdown，改一轮就完事。而公众号要的是「能直接粘」——样式内联、结构合规、图片就位。这两件事混在一个 prompt 里会互相拖累：排版规则几百行会稀释创作质量，创作产物的随意性又让排版没法确定性校验。所以拆开：

```
对话创作 ──产出──> 纯内容 Markdown（body 字段）
                       │ 用户点「保存到队列」
                       ▼
              队列「加工排版」= 后台任务（services/layout.py）
              POST /layout 秒回 task_id ──┐
                                          │ 前端轮询 GET /layout/{task_id}
              ┌───────────────────────────┘
              ▼  worker（_run_layout_job，自建 Session，Semaphore 串行）
              ① 读主题组件库 .md（提示词资产）
              ② LLM 装配 → 公众号 HTML
              ③ validate_gzh_html 确定性校验 → 有 ERROR 回修（≤2 轮）
              ④ 注入配图（<!--IMG:n--> → <img>）→ 写回 body_html
                       ▼
              预览确认（全屏 / 手机·平板·桌面三档）→ 推公众号草稿箱
```

> **为什么排版是异步任务**：单次约 2~3 分钟，超过前端 60s 超时。同步接口会让
> 前端「转圈→超时」，而后端照跑完（用户稍后打开发现已排好）。现改为
> 「提交任务秒回 + 轮询进度」，进度点：15 准备 → 30 装配 → 60/70 回修 → 90 装图 → 100。
> 任务表在进程内存（排版幂等，重启丢失即重跑），`Semaphore(1)` 串行防并发烧 token。

**关键决策：为什么把 gzh-design 技能库搬进后端当 prompt 资产，而不是写成 Python 模板**

先把技能目录里的 `.md`（`theme-index.md` / `common-components.md` / 7 个 `theme-*.md`）拷进 `backend/app/assets/gzh/`，由 `themes.py` 注册成主题（现共 **8 套**，第 8 套 `mashang-liaoliao`「码上聊聊」为品牌定制主题，见下）。这么做而不是解析成 Jinja/字符串模板，是因为**组件库的核心价值是语义判断，不是字符串填充**：

- 判定「这是观点型文章还是清单型」→ 决定用目录卡还是编号章节；
- 判定「哪句话是全文金句」→ 决定给哪句加下划线高亮；
- 判定「哪段适合配图」→ 决定在哪留 `<!--IMG:n-->` 占位。

这些是 LLM 的活儿，纯代码模板做不出来（做出来也很僵）。组件库交给 LLM 当「配方册」，让它自己挑组件、拼段落。

顺带一个现实约束：技能目录属于**宿主进程**，后端进程读不到、也 import 不了；而打包进后端又会让技能更新和后端发布耦合。折中是——只把**资产文件**（不是技能逻辑）拷进后端，`lru_cache` 加载，改主题只需替换 `.md` 文件，不动代码。

**确定性兜底（不能全信 LLM）**

排版 prompt 里写了 7 条硬契约（只输出 `<section>` 片段、样式内联、文字必须 `<span leaf="">` 包裹、禁 `<div>`/`class`/`@media`/`var(--x)` 等），但 LLM 仍会偶发出格。所以装配完立刻过一遍 `services/gzh_validate.py`（把技能脚本 `validate_gzh_html.py` 的 14 条禁用正则 + `_LeafChecker` 移植过来），**有 ERROR 就把校验结果回喂给模型重修，最多 2 轮**；回修后仍有 error 则如实返回，不伪造成功。

> **`<span leaf="">` 是硬要求**：公众号粘贴 HTML 时只保留白名单标签与内联样式，所有文字节点必须包在 `<span leaf="">` 里，否则整片样式丢失。这是整个排版引擎最不能省的一条，校验器专门数了 `span_leaf_count`。

**配图注入**：LLM 只在合适位置留 `<!--IMG:序号-->` 占位（不让它碰 URL，避免编造/幻觉图片地址）；后端按 manifest 把占位替换成真实 `<img>`（强制 `max-width:100%;height:auto;display:block;margin:0 auto`，公众号对图片尺寸很挑）。图片本身来自本地生图脚本（`IMAGE_SCRIPT`）或用户手动上传，都存 `content.images`（JSON）。

**两条配图通道（别混）**

| | AI 文内配图（`services/imagegen.py`） | 封面（`services/covers.py`） |
|---|---|---|
| 参数 | `--prompt --size --count --out` | `--title --sub --tag --style --size --out` |
| 出图 | 文生图模型，随机、要写提示词 | HTML 模板 + 无头浏览器截图，文字确定、秒出 |
| 产物 | 插在正文相关段落后 | **固定在正文最前**（头图/封面） |
| 存法 | `images[]`，`source="gen"` | `images[0]`，`source="cover"` |
| 配置 | `IMAGE_SCRIPT` | `COVER_SCRIPT`（默认 `scripts/make-cover.py`） |

两者契约完全不同，所以是**独立模块 + 独立配置**——把封面脚本塞进 `IMAGE_SCRIPT` 会因参数不匹配直接失败。前端「配图」区也分了「封面（头图）」和「文内配图」两个区块。

封面在 `images` 里的**位置即语义**：始终占 index 1（列表首位），所以 LLM 留的 `<!--IMG:1-->` 天然指向封面；`_image_manifest()` 会把第一张标成【封面/头图】并在 prompt 里要求放在正文最前。重复调 `/covers/generate` = 换封面（旧文件自动清理，不堆积）。

排版时自动带封面：`submit_layout_job(auto_cover=True)` 在 LLM 装配**之前**跑 `_ensure_cover()`——已有 `source=cover` 就跳过，没有就按正文自动出图并置顶。失败（脚本缺失/无浏览器）**只记日志不阻断排版**，封面是锦上添花。

**推草稿箱的图片处理**：公众号正文图不能引外链本地地址，必须走微信素材库。推草稿时 `push_wechat_draft` 带 `content_id`，后端用 `WeChatClient.transfer_inline_images()` 把正文里的本地图逐个 `cgi-bin/media/uploadimg` 换成微信 url，再取首图 `cgi-bin/material/add_material?type=image` 拿 `media_id` 当草稿封面（`thumb_media_id`）。两步用两套接口是微信的规定——正文图拿 url、封面图拿 media_id。

**品牌定制主题（第 8 套：`mashang-liaoliao` 码上聊聊）**

品牌方提供了一套视觉素材（`make-kit.py`，产出 9 个 PNG：4 种分隔符 / 章节条 / 3 种引导卡 / 文末三连条，主色 `#FF8A3D → #FF3B30` 渐变）。接入时做了一个关键取舍：

> **PNG 素材不直接用，而是用内联 HTML/CSS 等比复现成主题组件库。** 原因有三：① 公众号正文图受尺寸限制、不能随文字流自适应；② 9 个静态 PNG 无法覆盖不同标题长度/文案；③ 主题引擎的消费单位本来就是"内联 HTML 组件"，其它 7 套主题全是这个形态。复现后这些组件和其他主题完全同权、可被 LLM 按需装配。

落地方式与其它主题完全一致：`app/assets/gzh/theme-mashang-liaoliao.md`（设计变量表 + 26 个组件块 + 模板骨架 + 配方表 + 映射规则）+ `themes.py` 登记 + `theme-index.md` 登记。装饰性元素用 `<section>` 画渐变条、`<svg>` 画品牌气泡（公众号支持内联 SVG），空元素一律带 `<span leaf=""><br></span>`。

**加一套新主题的完整步骤**（改主题是资产增量，不用碰 Python 逻辑）：
1. 按 `gzh-skill.md`「添加新主题的规范」写 `theme-{id}.md`（五部分缺一不可）；
2. `themes.py` 的 `THEMES` 加一条（id/name/color/scenes/desc）→ 前端下拉自动出现；
3. `theme-index.md` 补一行（下划线 CSS 的权威来源）；
4. 本地过 `gzh_validate`（0 ERROR）+ 真实排版一次看效果。
5. **改完必须重启后端**（`themes.py` 是模块级常量、`load_theme_lib` 带 `lru_cache`，热改不生效，见开发指南坑 43）。

**作者占位符替换（排版时自动换真实值）**

组件库的签名区写的是占位符（如 `我是 {{作者名}}，{{一句话简介，如：…}}`），模型照抄装配后 body_html 里就带着它们，以前要用户自己进公众号手动替换。现在在排版阶段直接换掉：

- 作者信息存 `app_settings` 表（owner + key + value 的通用键值表，见 §6.2），系统设置页配一次；
- 排版请求带 `author_name` / `author_intro`（面板可临时覆盖），在 `layout_content` 写 body_html **之前**调用 `services/author.py::apply_placeholders()`；
- **替换走显式白名单**（`_KEYS = ("作者名","一句话简介","号名","slogan")`）：只有登记在 `_KEYS` 里的键会被替换，每个键一条正则吃掉 `，说明` 后缀（兼容 `{{作者名，未知则删整行}}` 这类变体），**绝不宽匹配所有 `{{…}}`** —— 组件库里有 40+ 种槽位（`{{顶部标签}}`/`{{简介段落}}`/`{{作者身份}}`/`{{LOGO占位}}`…），泛化替换会误伤。加新键只需改 `_KEYS` + 传入 mapping（开发指南坑 48）。

**加工排版面板的双栏编辑（2026-10-16）**

面板左栏从只读 Markdown 预览换成**可编辑**（`MarkdownEditor.vue`：NInput textarea + 加粗/标题/引用/列表快捷工具栏，自研不引库，保持依赖干净）；右栏预览 iframe 改 `contenteditable` 所见即所得。两条编辑链路都写回 `Content.body` / `body_html`，靠 `PATCH /content/items/{id}` 落库。

- **iframe 编辑的关键坑**：srcdoc 是响应式的话，编辑期每敲一个字 iframe 就整页重载、光标跳回开头。所以 `initialDoc` **只在打开面板 / 排版完成时设一次**，编辑期通过 `@load` 挂的 `input` 监听**防抖 300ms 单向回写** `editedHtml`，绝不回灌 srcdoc（开发指南坑 45）。
- **一致性**：显式「保存」为主；关闭面板有脏标记时拦截确认；**排版前自动存 body**（排版读的是库里的 body，不先存就排的是旧内容）；排版会重置 body_html，若右栏手改过会先弹窗确认。

**只读态：已发布任务 = 「排版详情」（2026-10-16）**

已发布（`QueueItem.status === 'published'`）的任务已经完成，不该还能改。此时面板从「加工排版」转为**只读的「排版详情」**：

- **只读由「队列状态」驱动，不是「内容」的属性**。`ContentItem` 不含队列状态（同一份内容可能挂在多个队列项上，各自发布进度不同），所以 `LayoutPanel` 的 `readonly` prop 由调用方 `QueueView` 按 `row.status === 'published'` 传入（开发指南坑 54）。
- **收干净编辑入口**（漏一个就还能改）：主题选择、一键排版、自动封面、公众号选择、推送、保存、作者信息行；左栏 `MarkdownEditor` → 只读 `MarkdownView`；右栏预览 iframe 的 `contenteditable` 置 `false` 且不挂 `oninput` 回写；下方 `ImageManager` 传 `readonly`（隐藏生成封面/换封面/删除/生成配图/上传/设为封面/删除，只留预览）。
- **保留只读动作**：复制富文本、预览宽度三档、全屏。
- 标题统一为「排版详情 · {标题}」+「已发布 · 只读」标识。注意面板有两条打开路径：列表「查看排版」（带 `row.status`）与推送兜底 `openLayoutFromContent`（语义是「还没排版，去加工」，恒为可编辑）。

**关注引导：点关注 / 长按关注 如何关联到账号（2026-10-16）**

需求：正文文末的「扫码 / 长按关注」要和真实公众号挂钩。做法是**把关注卡绑到公众号账号**（`wechat_accounts` 表，多号天然隔离）：

- 账号新增三列：`gzh_name`（对外号名，替换 `{{号名}}`；与内部展示名 `name` 语义不同故单开）、`slogan`（关注卡副标，替换 `{{slogan}}`）、`qrcode_path`（二维码相对路径，存路径而非 URL——URL 含 `?owner=` 且域名会变）。设置页可上传二维码（独立端点 `/settings/wechat/{id}/qrcode`，落 `data/uploads/qrcodes/{account_id}/`）。
- 排版请求带 `account_id`（空 = 默认号）。`layout_content` 在 `_inject_images` 之后依次做四步：**剥离开头关注卡 → 替换 `{{号名}}`/`{{slogan}}` → 注入二维码 `<img>` → 替换作者占位符**。
- **只在文末**：开头关注卡用 `<!--OPENING_FOLLOW_CARD-->…<!--/OPENING_FOLLOW_CARD-->` 标记包裹，后端整块剥离；模型丢标记时用「配对栈」求包含文案的最内层 section 区间兜底（嵌套 section 禁用非贪婪正则，见开发指南坑 49）。
- **二维码槽**用 `<!--QRCODE_SLOT-->` 标记包裹，未配二维码时整块删除（不留空白行）；`<img>` 放在 `<span leaf>` 之外（微信对 span 内块级 img 会套行内样式）。
- 替换统一走 `services/author.py::apply_placeholders(text, mapping)` + 白名单 `_KEYS`（见下）。
- **推送时单独转存二维码**：它不在 `content.images` 里，`transfer_inline_images` 不管它，必须在 `push_wechat_draft` 里用 `_resolve_wechat_account` 取账号后 `upload_image`，否则发布后外链失效（开发指南坑 50）。
- **主题局限**：只有 `mashang-liaoliao` 的组件库含账号占位符与二维码槽；其它 7 套无此机制（静默跳过，不报错）。`themes.py::load_theme_lib` 有幂等兜底注入，`.md` 被技能重新搬运也不会丢二维码槽。

### 4.2 小红书分支：只做文本规整，不做 HTML

`POST /layout` 的 `platform` 参数分流（`layout.py:dispatch`）：`gzh` 走上面的
HTML 装配管线；`xiaohongshu` 走 `_layout_xiaohongshu()`——小红书是纯文本 +
emoji + 图，没有富文本概念，所以：

- 轻量模型（`task="lightweight"`）把 Markdown 整理成可直接粘贴的笔记文本：
  标题 ≤20 字、正文分点 emoji 开头、话题标签归位到最后一行；
- **不过 HTML 校验器**（没有 HTML，`errors` 恒为空），产物存
  `content.layouts["xiaohongshu"]["text"]`，`layout_status` 同样置 `ready`；
- 配图不走 manifest 注入，前端按 §5 的生图能力另出 3-9 张竖图（3:4）。

即：同一套「异步任务 + 轮询」外壳，两种加工内核。队列项 `platform` 决定
点「加工排版」时走哪条分支。

## 5. 前端关键实现

**SSE 手动解析**（`api/chat.ts`）——`EventSource` 只支持 GET，对话是 POST：

```typescript
const reader = resp.body!.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''
for (;;) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  const parts = buffer.split('\n\n')
  buffer = parts.pop() ?? ''
  for (const part of parts) { /* 剥掉 data: 前缀 → SSEEvent */ }
}
```

**危险操作确认流**：`tool_confirm` 事件 → ChatMessage 挂 `pendingConfirm` → 消息流里渲染确认卡片 → 用户点确认调 `/api/chat/confirm`。发布队列页的「推草稿箱」按钮走同一条 confirm 通道（`tool_call_id` 用 `q_{itemId}` 合成）。

**移动端**：断点 768px。以上是侧边栏布局，以下是底部标签栏（图标 + 文字、`safe-area-inset-bottom`、内容区预留 76px 防遮挡）。所有表格加 `scroll-x` 防挤压。

**响应式交互：功能不丢，只换形态**。窄屏不是「把桌面布局压扁」，而是给核心功能区换一种交互：

| 页面 | 桌面（≥768px） | 窄屏（<768px） |
|------|----------------|----------------|
| 对话创作 - 会话列表 | 左侧常驻侧栏（`.conv-panel`，240px 列） | 左侧**抽屉**（`NDrawer`）+ 工具栏「☰ 会话」按钮；选中会话/新建后自动收起 |

实现约定（`ChatView.vue` + `components/ConvList.vue`）：① 列表本体抽成共用子组件 `ConvList`，桌面侧栏与移动抽屉复用同一份，重命名/删除等数据动作由父组件执行（子组件只 emit）；② 断点靠 `isMobile`（`window.innerWidth < 768` + `resize` 监听）驱动模板 `v-if`，**不是**纯 CSS 隐藏 —— 桌面不渲染抽屉 DOM；③ 触屏无 `hover`，`.conv-actions` 用 `@media (hover: none)` 常显（见开发指南坑 53）。

**对话页高度链：底部输入框钉死，消息区自己滚**。对话创作整页的高度是「`100vh - 130px`」的定高 grid（`grid-template-rows: minmax(0,1fr)` 锁行高），剩下空间由卡片吃掉（`flex:1`），卡片内部再分三段：工具栏（定高）/ 消息区（`flex:1; min-height:0`，自己滚）/ 输入框（定高）。这样无论消息多少，**输入框都钉在卡片底部且完整可见**，不会「消息一多就被顶出视口、要下拉才看得到」。注意是「**钉住 + 留白**」而非「紧贴」：卡片自身的 `padding-bottom`（约 12px）保留着，输入框与卡片底边之间留出呼吸空间。链路有三处容易被静默打断（`.n-card-content` 是 block、子组件根元素无 `data-v-*`、grid 行高默认 `auto`），改这块前先读开发指南坑 57。

**历史回显：思维链 + 工具痕迹 + 用量全落库**（2026-10）。assistant 消息的推理过程逐 delta 累积进 `Message.reasoning`，工具调用痕迹以展示型结构存 `Message.tool_calls`（`{"calls":[{id,name,arguments,result,status}]}`），token 用量落 `prompt_tokens`/`completion_tokens`。刷新/重开会话时完整还原：「思考过程」折叠块（**历史默认折叠、流式中默认展开**）、工具痕迹行、用量与费用行。两个关键设计：

- **思维链只给人看**：`build_context` 不回灌 `reasoning`（省 token，且避免不认 reasoning 的 provider 报错）；
- **不落 `role="tool"` 行**：工具执行结果回填进发起调用的那条 assistant 的 `tool_calls[i].result`（confirm 时按 `tool_call_id` 定位回填），工具痕迹跟着所属回复走；发给模型时再由 `_tool_calls_to_context()` 把展示结构转成 OpenAI 的 `assistant(tool_calls=[…])` + 逐条 `tool` 结果消息——**库里存的结构与喂给模型的结构是两套，边界在 service 层**。

**提问导航（`components/QuestionNav.vue`，DeepSeek 式 marker 轨）**：把当前会话里用户的每次输入列成目录，点击定位——长会话里「我之前问了什么」一眼能看到。形态是「**默认不占空间，hover 才展开**」：宽屏（≥1200px）对话区右缘只保留一列 ~20px 的 marker 轨，每条提问一根小横线（当前阅读位是主色加粗条，随消息区滚动联动，只认 user 消息）；鼠标经过某根 marker 时，向左弹出 288px 的概要浮层（fixed 定位、垂直中心对齐该 marker 并钳制在视口内，单行截断 + 悬停项右侧小横线指示），点击 marker 或浮层项即滚动定位并闪烁高亮；鼠标离开 160ms 后收起（延迟是给鼠标从 marker 移进浮层留时间）。窄屏没有 hover，功能不丢、只换形态：收成对话卡片顶部的横向 chips。两种形态复用同一份数据与同一个 `jump` 事件，实现细节见坑 59。

**对话 ⇄ 队列双向跳转**：保存到队列时上报 `conversation_id` + `msg_id`（assistant 消息的 id 即前端预生成的 `assistant_msg_id`，落库时直接当主键，两边 id 天然对齐）；队列页「回到对话」跳 `/chat?conversation_id=…&msg_id=…&content_id=…`，ChatView 打开会话、滚动定位并闪烁高亮那条回复，成功后清 query 并显示「← 返回发布队列」闭环条；会话已删则兜底（不白屏 + 提示 + 清 query）。URL 契约见 API 文档「对话 ⇄ 队列双向跳转」。

**新手引导（`components/GuideTour.vue` + `stores/onboarding.ts` + `onboarding/steps.ts`）**

一次性讲清系统怎么用：**首次访问自动跑一遍聚光灯引导**，看完/跳过即写 `localStorage.cwb_onboarding_done`，之后永不再自动弹；侧栏底部（移动端在 header）常驻「❓ 新手引导」按钮可随时重看。

- **为什么自研**：项目用的 naive-ui 2.45 **没有 `NTour`**（只有静态步骤条 `NSteps`），引第三方 tour 库又过重。自研可控「只弹一次的时机 / 跨页跳转 / 窄屏行为」三件最要紧的事。
- **聚光灯挖洞**：一个透明框 + `box-shadow: 0 0 0 9999px rgba(0,0,0,.55)` 铺满四周，比「四块遮罩拼」简单且过渡动画天然顺滑。
- **跨页定位**：每步先 `router.push({name})` 再**轮询等锚点元素出现**（页面是懒加载的，跳完立刻 `querySelector` 常拿不到，最多等 1.6s）；目标在视口外先 `scrollIntoView`，再 60ms 低频轮询重算 rect（页面里有多个滚动容器，轮询比挂一堆 capture 监听更省心）。
- **兜底**：锚点找不到 → 退化成屏幕居中的无高亮卡片，不闪烁不报错。锚点优先用视图里**已有的语义 class**（`.chat-toolbar` / `.composer` / `.queue-header` / `.mobile-tabbar`），不为了做引导改页面结构。
- **窄屏**：气泡固定贴底；若高亮目标也贴底（如移动端底部导航），气泡自动改贴顶（`dock-top`），否则会盖住目标。

**深浅主题切换**（`stores/theme.ts` + `styles/theme.css`）：两套来源、三条链路：

```
① CSS 变量层：styles/theme.css 定义 --app-* 语义变量（表面/边框/文本/主色阶/功能色）
   :root 默认暗色，:root[data-theme='light'] 亮色，切主题 = 切 <html> 的属性
② Naive UI 层：App.vue 用 :theme="naiveTheme" 挂 darkTheme/lightTheme，
   配 computed GlobalThemeOverrides（两套手调色板），组件内部颜色跟主题
③ 状态层：Pinia store 管 mode（light/dark/system，localStorage cwb_theme，
   缺省 system），resolved 由 matchMedia 得出，toggle() 一键切换
```

三个关键点：

- **不用 Naive 的 `--n-*` 变量**：那些变量由各组件的 cssr 定义在**组件根元素**上，
  自有的 scoped 样式不一定能继承到，不可靠。所以自建 `--app-*` 体系，9 个视图的
  硬编码色全部变量化（40 项显式映射 + 15 项 rgba，见 `开发指南` 坑 35~37）。
- **防首屏闪主题**：`index.html` 里挂载前跑一段同步内联脚本，按 `cwb_theme` /
  `prefers-color-scheme` 先设好 `<html data-theme>`，否则刷新时会先闪一帧相反主题。
- **SVG 属性不认 `var()`**：`fill="var(--x)"` 作为 presentation attribute 无效，
  图表颜色一律 `:style="{ fill: 'var(--x)' }"` 绑定。

## 6. 数据模型

```
Conversation 1 ─── N Message        （会话与消息，含工具调用记录）
Content      1 ─── 1 QueueItem      （成品与队列项，content_id 关联）
```

- `Message.tool_calls` 记录 Function Calling 全过程（展示型结构 `{"calls":[{id,name,arguments,result,status}]}`），前端刷新后能还原工具轨迹；`Message.reasoning` 存思维链全文（只回显、不回灌模型）；`prompt_tokens`/`completion_tokens` 存单条用量；
- `QueueItem.checklist`（JSON）存分平台检查清单的勾选进度；
- `QueueItem.wechat_media_id` 存推送成功后草稿箱返回的 media_id，用于去重。

`Content` 按「内容 / 排版」两层语义分字段（注意别混用）：

| 层 | 字段 | 含义 |
|---|---|---|
| 内容 | `body` | 对话产出的纯内容 Markdown |
| 内容 | `summary` / `conversation_id` | 摘要 / 来源会话（回填后队列项可跳回对话；来源消息 id 存 `meta.msg_id`，队列列表一并透传） |
| 排版 | `body_html` | LLM 装配出的公众号 HTML |
| 排版 | `theme` / `layouts` | 主题 id / 各平台产物（如 `layouts["xiaohongshu"]["text"]`） |
| 排版 | `images` | 配图清单（JSON：id/path/url/alt/source/prompt/position） |
| 排版 | `layout_status` | `none` → `ready`（加工完成） |

`QueueItem.status` 流转：`draft`（新建待加工）→ `ready`（待发布）→ `published` / `archived`。

另有一个**独立的** `Content.processing` 字段（`""` / `layout` / `image`）表示「正在加工」，
与 `layout_status`（产物态）、`QueueItem.status`（发布生命周期）**三者分离**：把 processing
塞进 status 会污染所有状态筛选/统计。队列页据此显示「排版中/生图中」标签并禁用操作。

**`processing` 的解除路径必须有三条**（否则标记残留会把 UI 永久锁死，实测踩过）：
① worker 的 `finally`（正常/异常收尾）；② **服务启动**时 `recover_stuck_processing()`
统一清残留（进程重启/沙箱休眠时任务没了但标记还在）；③ **前端手动取消**
（`POST /content/items/{id}/cancel-processing`，面板关闭时也自动触发）。
配套：队列页轮询**只定向刷新当前页的处理中行**（不整表重载），组件卸载/无加工任务即停；
队列列表**分页**（`page`/`page_size` + `total`，筛选在后端做）。

一期 SQLite 够用（WAL 模式、异步驱动）。模型新增列靠 `session.py` 的 `_SQLITE_COLUMN_PATCHES` 自动补（`create_all` 不会给已存在的表加列）。上量后切 Postgres：改 `DATABASE_URL` + 装 asyncpg 即可，模型层零改动。

## 6.1 公众号账号（多号 + 默认号）

凭证不再只能写死在 `.env`：`wechat_accounts` 表存多号（名称/appid/secret/主页/是否默认/验证时间），
「系统状态」页可增删改 + 测试连通性。推送时的凭证解析顺序：

```
显式 account_id  →  is_default=True 的号  →  .env 的 WECHAT_APPID/SECRET  →  都没有则报错
```

- **secret 不回传明文**：接口只给 `secret_set` 布尔，`PUT` 时留空 = 不改；
- 默认号**全局唯一**（设默认时先把其它清掉；删默认号自动把剩下的提为默认）；
- access_token 缓存 key 是 `wechat:token:{appid}`，多号天然隔离；
- **IP 白名单填「微信实际出网 IP」**，不是 SSH 反向隧道服务器的 IP ——
  反向隧道只做入站转发，不承载出网流量。
- **固定出口代理（解决沙箱动态 IP 池）**：沙箱/容器出网 IP 是**动态池**
  （实测一次采样就探到 20+ 个 IP，见 `deploy/probe-egress-ip.sh`），而微信只接受**单个 IP**
  白名单（不收 CIDR），逐个加白根本追不上。做法是让**仅微信请求**走一台**固定公网 IP**
  的机器出网：

  ```
  后端(沙箱) --socks5://127.0.0.1:10800--> [ssh -D] --SSH--> 固定IP机器 --> api.weixin.qq.com
  ```

  - 隧道由 `deploy/proxy-guard.sh` 建立并**断线自愈**（每 15s 校验实际出口 IP，不符即重建）；
  - 后端设 `.env`：`WECHAT_PROXY=socks5://127.0.0.1:10800` +
    `WECHAT_PROXY_EXPECT_IP=49.233.223.252`；
  - **只作用于 `services/wechat.py`**（微信请求），LLM/生图等其他出网流量不受影响；
    留空 `WECHAT_PROXY` 则完全直连（原行为）；
  - 该模块对**经代理时的瞬断**（`httpx.TransportError`）自动重试 1 次，覆盖「SSH 隧道
    偶发断流导致 multipart 上传失败」；
  - 只需把 `WECHAT_PROXY_EXPECT_IP` 这**一个 IP** 填进公众号后台白名单；
  - 系统状态页「测试连通」返回的 `egress.ip` 即当前实际出口，可直接抄进白名单。

## 6.2 通用设置 `app_settings`（作者信息等）

为什么要单开一张键值表，而不是往 `wechat_accounts` 加列：作者信息**不属于某个公众号**，加列会让语义错乱（多号时还歧义）。`app_settings` 是 `(owner, key, value)` 结构 + `(owner, key)` 唯一索引，承载「一次配置、全局复用」的设置，后续加项零成本。

当前键：`author_name` / `author_intro`（排版时替换正文占位符，见 §4.1）。接口：`GET/PUT /api/settings/author`。表结构同步在 `models/settings.py`；新表由 `Base.metadata.create_all` 在启动时自动建 —— **记得在 `models/__init__.py` 导入，否则建不出来**（开发指南坑 46）。

## 7. 视频渲染管线（真实渲染，已上线）

```
口播脚本 → edge-tts 配音（SentenceBoundary 句级时间戳）
        → 按句切音频（wav 无损切片）
        → PIL 绘制渐变卡片（自适应字号大字幕）
        → Ken Burns 运镜（zoompan 逐段推/拉）
        → ffmpeg concat 合成 → mp4
        → [可选] 口播稿写 SRT → mov_text 软字幕轨封装（画面不动）
```

要点：
- **字幕不用 whisper**：edge-tts 合成时直接吐 SentenceBoundary，时间轴是免费副产品；
- **配音分段合成**：整段几千字一次性丢给 edge-tts 容易返回「No audio was received」，
  所以按换行/句末标点切成 ≤400 字的段逐段合成（失败自动重试 3 次），mp3 按字节拼接、
  句级时间轴按 ffprobe 实测时长累加偏移；
  画面文字用 PIL 画进卡片，不跟 ffmpeg drawtext 的字体/转义/换行打架。
- 任务落 `render_jobs` 表（SQLite），进度实时回写，重启不丢；启动时把中断的
  孤儿任务统一标 failed，可一键重试。
- 串行渲染（Semaphore=1）防 CPU 争抢；720p 成片，10 秒视频约 3-6 秒渲染。
- **口播稿 → 内嵌软字幕轨**：渲染最后一步把口播稿逐句写成 SRT，
  `ffmpeg -c:s mov_text -metadata:s:s:0 language=chi` 封成 mp4 第二条流。
  画面（含 PPT 真图）一个像素都不动，字幕在播放器里可开关、可导出。
  时间轴取 `Scene.start/end`（配音实测时长），是句级而非字级。
  `subtitle: false` 可关；`concat_clips` 的 copy / filter 两条降级路径都带字幕轨。
- PPT 转视频：`services/ppt_parser.py` 用 python-pptx 抽每页备注（优先）/文字生成
  口播稿，同时拆出每页标题+要点作为 `visual_scenes` 随任务入库；渲染时按镜头数
  比例映射到时间轴，画面画「SLIDE 卡片」（标题+要点列表），口播句只进配音。
  用户改了口播稿则自动退回大字幕模式，避免图文错位。
- **PPT 画面用真图**：上传的 pptx 经 LibreOffice 无头模式渲染成每页 PNG（按内容
  md5 缓存），视频画面 = 真实幻灯片 + 高斯模糊填充背景 + Ken Burns 运镜；没装
  LibreOffice 或转换失败时自动退回标题+要点的 PIL 文字卡片。
- 成片经 `/api/video/outputs/{filename}` 提供预览/下载（文件名白名单防路径穿越）。

### 7.1 声音复刻（用自己的声音配音）

```
录音（10~30s）→ 清洗（重采样/高通/剪静音/响度归一）→ 声学指纹（给用户反馈）
              → 提取音色（XTTS 预热 或 云端建音色）
              → voice.json 落盘 → 音色出现在下拉框（voice = clone_<id>）

渲染时：voice 以 clone_ 开头 → 交给 services/voices.synth_clone()
        文本按 ≤80 字切段 → 逐段合成 → concat → ffprobe 实测累加出时间轴
```

**为什么独立成模块**：复刻的输入输出契约（一段文本 → 一条 mp3 + 句级时间戳）
和 edge-tts 完全一致，所以把复刻音色伪装成"一个音色名"，`video_pipeline`
只需在 `synth_voice()` 门口加一个 `is_clone_voice()` 分支，其余 400 行管线
一行不动。这是改动量最小的接法。

**三条后端路线**（`VC_PROVIDER`）：`edge`（不复刻）/ `xtts`（本地 Coqui
XTTS-v2 零样本克隆，CPU 可跑、零成本）/ `cloud`（云端 API，效果最好）。
Provider 用同一套接口（`train` + `synth`），新接一家厂商只写一个类。

**踩过的坑**：
- XTTS **不返回时间戳**（edge-tts 会吐 SentenceBoundary），所以本地路线
  只能按段实测累加 —— 这就是必须切短段（≤80 字）的原因，段长了漂移明显；
- XTTS 会**连参考音频的噪声一起复刻**，所以上传后强制做音频清洗，这步
  对最终效果的影响比选哪条路线还大；
- 「训练」其实是**预热**：零样本克隆不需要训练，加载模型 + 算一次 reference
  embedding 就是全部。把它放进训练阶段，渲染时才是热启动。

## 8. 用户认证与数据隔离（owner）

**演进**：隔离接缝先落地——所有业务表早有 `owner` 列（Conversation / Content /
QueueItem / LlmUsage / WeChatAccount / RenderJob），单租户期跑 `"default"`。
用户模块上线时只替换唯一接缝 `app/core/tenant.py`：从「客户端自称」换成
「服务端解析」，53 处 `Depends` 机械改名（`current_owner` → `current_owner_id`，
薄封装返回 `user.id`，端点函数体一行不动），路由 / 服务 / 模型层零改动。

**现在的形态**：

```
请求 ──> app/core/tenant.py ──> owner（= 登录用户 id）
              │
              ├─ 普通请求：Authorization: Bearer <JWT> → current_user → User 对象
              ├─ 浏览器直链：?o=<uid>&sig=<hmac> → link_auth（HMAC 校验，Bearer 兜底）
              └─ 都没有 → 普通端点 401；直链端点 404（不泄露存在性）
```

- **安全原语集中在 `app/core/security.py`**：bcrypt 密码哈希（直接用 bcrypt 库，
  不引 passlib——1.7.4 与 bcrypt 5.x 有兼容雷）；JWT(HS256) 签发/校验；
  直链 HMAC 签名。密钥优先级 `JWT_SECRET`（.env）> `data/secret.key`
  （首次启动自动生成并持久化，重启不失效、不进 git）。
- **用户 id 直接当 owner**：`User.id = uuid4().hex`（32 字符）塞进现有
  `owner String(64)` 列，无 schema 迁移、无 Alembic。
- **存量认领**：首用户注册同事务内 `UPDATE ... SET owner=uid WHERE owner='default'`
  （含 NULL）+ 旧式 `?owner=default` URL 逐条重签（contents 的 images/layouts/body_html）
  + voices 目录搬迁（`profiles/` → `owners/<uid>/profiles/`，`profiles_dir()`
  早有 owners 分支，纯数据操作）。
- **直链为什么不放 JWT**：全账户凭证会进 HTML / Referer / 浏览器历史，且 7 天
  过期会让存量持久化 URL 集体失效（WeChat 转存靠字符串精确匹配）。HMAC 不过期，
  泄露代价限定在「该用户的这一个路径」，小一个量级。
- **slides 撞目录**：幻灯片图按 `md5(pptx)[:16]` 命名，跨用户相同 → `PptSlideClaim`
  表懒认领（无记录登记为当前用户，有记录且归属不符 404），配合 `link_auth` 双保险。

**各层怎么落的**：

| 层 | 隔离方式 |
|---|---|
| 队列/内容（`queue.py` 9 端点） | 每端点 `Depends(current_owner_id)`；建内容/队列项带 `owner`；查询、删除、统计全部按 owner 过滤；直连 GET 别人的内容 = 404（与「不存在」同响应） |
| 排版配图（`layout.py`） | `_get_content` 校验归属；`<img src>` 的 URL 由服务端拼 HMAC 签名（`link_url`）；静态服务端点走 `link_auth` 二次校验 |
| 视频（`tools.py` 7 端点 + `render.py`） | `get_job(job_id, owner)` 过滤；worker 跑任务时把 job 的 owner 一路传给渲染/配音；成片下载链接走 `link_url` 签名 |
| 公众号（`settings.py` 6 端点） | 多号表按 owner 过滤——**appid/secret 隔离的关键**；工具侧 `_resolve_wechat_client` 显式传 account_id 也校验归属 |
| 对话（`chat.py` 7 端点） | 会话 CRUD / 流式 / confirm 全部按 owner |
| AI 用量（`usage.py` + `services/usage.py`） | 统计/明细/TOP 会话加 `owner ==` 条件 |
| 音色库（`voices.py`） | 目录按 owner 隔离：`VOICE_DIR/owners/<owner>/profiles/`（存量搬迁后统一走这条）；克隆任务表 key 为 `f"{owner}:{profile_id}"`；试听 URL 走 `link_url` 签名 |

**前端**：`stores/auth.ts` 管登录态（token 存 localStorage `cwb_token`）；
`main.ts` 挂载前 `bootstrap()` 验 token 防刷新闪登录页；路由守卫未登录重定向
`/login?redirect=...`；`api/http.ts` 请求拦截器带 Bearer、401 清 token 回登录页
（登录页自身的 401 不跳，防死循环）；SSE（`api/chat.ts`）同款带头。

**路由层级**：登录/注册是**顶层路由**，工作台五个页面挂在 `layouts/AppShell.vue`
的 `children` 下，`App.vue` 只留主题 Provider + 唯一一个 `<RouterView/>`。
不要在外壳层用 `v-if="isAuthenticated"` 分叉两个 RouterView —— 登录态一变，
当前路由组件会被销毁重建（注册后的「存量接管摘要」因此被清空，见开发指南坑 61）。

**已实测**：注册 / 登录 / 邀请码三分支 / 限流 / 首用户认领（URL 重签 + 目录
搬迁）/ 直链签名通过与拒绝 / slides 撞目录 404 / 越权 404 / 401 语义 ——
`tests/test_auth.py` 11 项 + 存量测试共 25 项全绿。
