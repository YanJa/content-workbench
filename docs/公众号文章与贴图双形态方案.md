# 公众号「文章」与「贴图」双形态方案

> **问题**：现在推送草稿只产出「文章」（`article_type=news`），用户需要也能发「贴图」（`article_type=newspic`，官方叫**图片消息**）。
> **本文只做方案，不改代码。**

---

## 一、先把官方规则讲清楚（依据：draft/add 文档）

两者的请求结构**完全不同**，不是换个字段就行：

| | 文章 `news` | 贴图 `newspic` |
|---|---|---|
| `title` | 必填，**≤32 字** | 必填，**≤32 字** |
| `content` | **必填**，HTML 正文 | 可选，**仅支持纯文本 + 部分特殊标签（如商品）** |
| `thumb_media_id` | **必填**（永久 MediaID） | **不适用** |
| `image_info.image_list` | ❌ 不用 | **必填**，`image_media_id` 列表；微信接口 1–20 张，**本产品收敛为 5–6 张（硬上限 6）**，首张即封面 |
| `cover_info` | 可选 | 可选（支持 1_1 / 16_9 / 2.35_1 裁剪） |
| `need_open_comment` | 0 关闭（默认）/ 1 打开 | 同左 |
| 正文图片 | 必须来自 `media/uploadimg`（返回 url） | 不需要 |

**三个硬约束（方案必须围绕它们设计）**：

1. **贴图的图必须是「永久素材」** → 走 `material/add_material?type=image` → 拿 `media_id`。
   这和正文图用的 `media/uploadimg`（返回 url）是**两套不同接口**，不能混用。
   好消息：项目里 `upload_thumb()` 已经在用这个接口，**可直接复用**。
2. **贴图至少 1 张图**；微信接口最多 20 张，但**产品口径 5-6 张、硬上限 6 张**，首张就是封面。
3. **`content` 在贴图里不能放 HTML 正文** —— 只支持纯文本。这意味着**排版好的 HTML 不能直接塞进去**。

---

## 二、现实盘点：我们的数据够不够发贴图？

我查了开发库的实际数据：

| 图片张数 | 内容篇数 |
|---|---|
| 0 张 | 1 篇 |
| **1 张（只有封面）** | **4 篇** |
| 2 张 | 1 篇 |
| 4 张 | 1 篇 |

图片来源：`cover` 4 张、`gen`（AI 生成）2 张、`upload` 3 张。

**结论：现状下大部分内容只有 1 张封面图。** 技术上 1 张图就能发贴图（首张即封面），但**1 张图的「贴图」体验很差** —— 贴图的本质是「多图流」，单图贴图在微信里表现接近一张图片卡片。

生图入口的张数上限已放宽到 **6**（`NInputNumber :max="6"`），一次生成正好覆盖 5-6 张的贴图口径。

**所以这个方案不只是「支持一个字段」，还要解决「图从哪来」。**

---

## 三、方案设计

### 3.1 数据模型

**不新增表**，在 `Content` 上加一个字段（沿用它已有的 `layouts` JSON 快照思路）：

| 字段 | 位置 | 说明 |
|---|---|---|
| `article_type` | `Content` 新增列，默认 `"news"` | `news` / `newspic`，标记这篇内容的发布形态 |
| `images` | 已有 | 贴图模式下的图序即 `images` 数组顺序，**第 0 张为封面** |

为什么放 `Content` 而不是 `QueueItem`：发布形态是「内容属性」（这篇东西天生是图文还是贴图），不是「发布任务属性」。同一篇内容进不同平台的队列，形态应该恒定。

> 如果要支持「同一篇内容既发文章又发贴图」，则需要把形态放到 `layouts` 里做多快照。**MVP 不做**，一个内容一个形态，够用且简单。

### 3.2 后端改动

```
services/wechat.py
├─ upload_permanent_image()          # 新增：复刻 upload_thumb 的调用，但明确语义
│                                     #   （其实 upload_thumb 就是 add_material，只需重命名/复用）
├─ add_draft()                       # 改造：按 article_type 分支
│    ├─ news    → 现有逻辑不动
│    └─ newspic → 校验 1<=n<=6 → 逐张上传拿 media_id
│                 → payload 只带 title/content(纯文本)/image_info/评论开关
│                 → 不带 thumb_media_id
│
tools/builtin.py :: push_wechat_draft
├─ 新增参数 article_type (enum: news/newspic)
├─ newspic 分支：
│    ├─ 少于 1 张图 → 直接拒绝，给可操作提示（"贴图至少需要 1 张图"）
│    ├─ 超过 6 张 → 只取前 6 张，返回里说明截掉了几张
│    ├─ 不传 thumb_media_id
│    └─ content 传纯文本（取 body 的纯文本，不是 body_html）
│
routers/queue.py + schemas
└─ 推送接口透传 article_type
```

**关键实现细节（容易踩的坑）**：

1. **`content` 要用纯文本，不是 `body_html`**
   贴图的 `content` 不支持 HTML。取 `Content.body`（Markdown）后转纯文本，或直接传 `summary`。建议：`content` 传去掉 Markdown 标记的纯文本，**不要截断成摘要**（用户可能想写一段图注）。

2. **图片上传失败要「部分成功」还是「全失败」**
   建议**全失败**（任一张上传失败就中止，不留半截草稿）。理由：贴图是整体作品，缺图比失败更糟。

3. **同一张图重复上传会消耗素材库配额**
   微信永久素材有数量上限（图文 5000 / 图片 5000 量级）。**应缓存 `local_path → media_id`**，避免每次推送都重传。建议在 `Content.meta` 或新表里存映射。

4. **`need_open_comment` 两者都支持**，刚统一默认打开，直接复用。

### 3.3 前端改动

```
LayoutPanel.vue（加工面板）
├─ 顶部加「发布形态」切换：文章 / 贴图
│   ├─ 切到「贴图」时：隐藏主题选择、隐藏排版按钮（贴图不需要排版）
│   └─ 显示图片管理区（多图排序、增删、首图标「封面」）
├─ 生图数量上限：贴图模式下放宽到 20
└─ 推送按钮文案随形态变化（"推微信草稿箱" → 语义不变）

QueueView.vue
└─ 行内展示形态标签（文章 / 贴图），推送时带 article_type
```

**交互要点**：

- 切到贴图时**不要把 body_html 丢掉**（用户可能切回来），只是不推送它
- 图片排序用拖拽，首张加「封面」角标
- 推送前二次确认里**明确写「将以贴图（图片消息）形式推送，共 N 张图，首张为封面」**

### 3.4 图片从哪来（这是真正的瓶颈）

按推荐优先级：

| 来源 | 现状 | 建议 |
|---|---|---|
| **AI 生成** | `genCount` 上限 4 | 贴图模式放宽到 20（分批生成，注意成本与配额） |
| **本地上传** | 已有单图上传 | 支持一次选多张 |
| **从成稿插图取** | 排版产物里有 2–4 张 | 一键「复用成稿配图」 |
| **封面模板** | `covers.py` 生成 | 贴图不太需要封面模板 |

## 四、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| **账号权限** | `draft/add` 文档标注「公众号服务号 ✔」，个人订阅号实际可用但受限；贴图（图片消息）对**订阅号**的支持需实机验证 | 见下方「已有实测」，仅剩 newspic 待验 |
| **1 张图的贴图很尬** | 现有数据多是单图 | 前端提示「贴图建议 3 张以上」，但**不强制** |
| **永久素材配额** | 每次推送都上传会累积 | 必须做 `media_id` 缓存 |
| **纯文本 content 表达力弱** | 贴图正文不能排版 | 这是微信的限制，接受它；如需长文就该用「文章」 |
| **两种形态的心智负担** | 用户可能分不清 | 默认「文章」，贴图作为显式选项，配一句说明 |

### 4.1 已有实测（2026-10-22，只读探测，未产生任何副作用）

对当前默认公众号「码上聊聊」（`wxb2957976...`，已认证）做了只读探测：

| 探测项 | 结果 | 意义 |
|---|---|---|
| `access_token` | ✅ 获取成功 | 凭证与 IP 白名单均正常 |
| `draft/count` | ✅ `total_count: 0` | 草稿接口连通正常（历史草稿已被群发移除） |
| `draft/batchget` | ✅ 正常返回 | 草稿读写通路可用 |
| `material/get_materialcount` | ✅ **`image_count: 177`**、`news_count: 1` | **永久图片素材通路已验证可用**（贴图依赖的正是这个），且已有 177 张存量 |
| news 形态推送 | ✅ 历史成功 3 次 | 文章通路已生产验证 |

**结论**：贴图方案的两个前置条件 ——「永久素材上传接口可用」和「草稿接口可用」—— **都已实测通过**。唯一未验证的是 **`article_type=newspic` 本身是否被该账号接受**，这必须真发一次才能确认（会产生一条真实草稿）。

**素材配额提醒**：177/5000 已用约 3.5%。若每篇贴图都重传 5 张图，200 篇就会打满。**`media_id` 缓存不是优化项，是必需项**。

## 六、建议的落地顺序

1. **先做 P3 探测**（0.5 天）—— 只差「`newspic` 是否被账号接受」这一项。其余前置条件（token、草稿接口、永久素材上传）都已实测通过。
   探测方式：上传 1 张图拿 `media_id` → 调一次 `draft/add` 带 `article_type=newspic` → 看返回。**会产生一条真实草稿**，验完在后台删掉即可。
2. 再做 P0 + P1（1.5 天）—— 主链路可用。
3. P2 作为优化后续补。

**如果 P3 探测发现账号不支持贴图**，方案降级为：只做「文章」形态，但把 `article_type` 字段留好（默认 `news`），未来账号升级后无缝打开。

## 七、与「评论开关」的关系

刚已完成的改动（`need_open_comment` 默认 1）对两种形态**都生效**，贴图实现时不用重复处理，直接复用 `add_draft(need_open_comment=...)`。
